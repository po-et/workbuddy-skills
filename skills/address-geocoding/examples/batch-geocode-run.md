# 示例：订单地址批量转坐标，再算门店 5 公里配送范围

> 对话为示例。为了离线演示，接口换成了本地假服务 `mock_geocoder.py`，坐标是假数据；输出是脚本对下列样例的真实运行结果，未手改。地址里的「查无此地」「偶发故障」「超时」「限频」是故意触发假服务故障的测试词。

## 对话

**用户**：我有一份订单表，想把收货地址转成经纬度，再看看哪些单在我们两家店 5 公里内。

**助手**：先确认三件事：
1. 地址在哪一列？有没有单独的城市列？
2. 两家门店的坐标有吗？是从哪个地图上取的（决定坐标系）？
3. 腾讯位置服务的 key 已经申请好、并开了 WebService 能力吗？key 请只放在你电脑的环境变量里，不要发给我。

**用户**：地址列叫「地址」，城市列叫「城市」。门店坐标是在腾讯地图上取的。key 有了。

**助手**：门店坐标来自腾讯地图，和接口返回的都是 GCJ-02，可以直接算距离。按「清洗 → 预演 → 小批量 → 全量 → 复核」来。

## 第 3–4 步：真正请求（这里指向本地假服务）

```bash
export TENCENT_MAP_KEY=local-test
python3 scripts/geocode_batch.py geocode orders.csv --column 地址 --city-column 城市 --out geo.csv \
    --run --base-url http://127.0.0.1:8765 --timeout 1 --retry-status 9001 --interval 0.05 --cache cache.json
```

```
完成：共 13 行｜实际请求 11 次｜成功 6｜低可信 4｜失败 2｜未请求 1 → geo.csv
  失败原因：status=9002 模拟：查询无结果 ×1
  失败原因：请求超时（1.0 秒）（已重试 2 次） ×1
```

A010 第一次遇到 HTTP 500、A013 第一次遇到「请求过快」，都在重试后成功；A012 与 A001 清洗后相同，只请求了一次。带同一个缓存再跑一遍，只会重新请求两条失败的：

## 第 5 步：到门店的距离

`stores.csv`：

```
name,lat,lng
科技园店,22.5405,113.9530
福田店,22.5367,114.0500
```

```bash
python3 scripts/geocode_batch.py distance geo.csv --stores stores.csv --radius-km 5 --out dist.csv
```

```
完成：13 个点，2 家门店，没有可用坐标 3 行；半径 5.0 千米内 9 个（福田店 9；其中坐标低可信 3 个） → dist.csv
```

## 助手的交付物（按输出契约）

```
【处理摘要】13 行｜实际请求 11 次（去重、缓存后）｜成功 6｜低可信 4｜失败 2｜未请求 1
【结果文件】geo.csv（坐标系 GCJ-02）；dist.csv（最近门店、直线距离、是否在 5 千米内）
【需要人工复核】
  1. 城市不一致 1 行（A004）：确认是否发往杭州；若是，这单不属于两家店的配送范围
  2. 地址太笼统 3 行（A005–A007，只到区或片区）：回原订单补门牌或小区名后单独重跑
  3. 查不到 1 行（A008）：地址疑似有误，联系收货人确认
  4. 超时 1 行（A011）：网络恢复后带 --cache 重跑，只会补这一条
  5. 空地址 1 行（A009）：补地址
【距离结论】5 千米内 9 单，全部最近福田店；其中 3 单坐标低可信（A005–A007），不能据此承诺配送。
  直线距离不等于骑行或驾车距离，最终以路网距离或实际配送时长为准。
【提醒】调用量与费用以腾讯位置服务控制台为准；key 只放环境变量。
```
