# 线上故障应急助手

定位一句话：**故障期间不研究代码，先止损、再定界、后定因，最后交代。**
这是「研发效能」系列里应急场景的入口。何时用：告警响了、有人在群里喊线上挂了、要交故障简报或复盘时，先在下表对号入座。表里的子技能装了就直接调用（自带脚本、纯标准库，一条 `python3` 命令出结果），没装就按本页的精简方法做，并告诉用户可以在 SkillHub 搜对应 slug 安装。

## 应急四拍（顺序不要换）

```
1 止损：能回滚先回滚，不行就限流 / 降级 / 切流量，别边扛边查
2 定界：影响哪些接口、多少比例请求、哪些用户、从几点几分开始
3 定因：列可证伪假设 → 先验最快能验的 → 拿日志、指标、变更记录对齐
4 交代：进行中发简报，结束后做复盘，改进项挂人挂日期挂验收方式
```

## 意图 → 方法 → 子技能

| 用户在说什么 | 先做什么 | 子技能（SkillHub slug） |
|---|---|---|
| 告警刚响、线上挂了，先干什么 | 按四拍走；同时开一份时间线，把告警时间、症状、已做动作、执行人逐条记下来 | 线上排查简报 `incident-brief-sre` |
| 错误是什么时候开始变多的 | 日志或指标按分钟聚合，滑动基线 3σ 标出异常起点、峰值与恢复点，再与变更时间对齐 | 日志突变检测 `log-anomaly-3sigma` |
| 几台机器、几个服务的日志对不上 | 多格式多时区时间戳归一后合成一条排序时间线，标注来源、级别与错误爆发点 | 日志时间线重建 `log-timeline` |
| 日志刷屏，看不出哪条是新错误 | 变量位抽象成模板后计数——最常见的是噪音，最少见的往往才是这次的新错误 | 日志模板聚类 `log-pattern-cluster` |
| 影响面有多大、哪些接口受影响 | 访问日志出接口级报表：请求量、错误率、5xx、P95/P99、高峰时段、Top IP | 访问日志统计 `access-log-stats` |
| 是不是数据库拖的 | 慢查询日志按指纹聚合出 Top SQL，附扫描行数与缺索引、无 WHERE 等改法 | 慢查询摘要 `sql-slow-query-digest` |

| 这块代码谁最熟、改动最频繁 | git 历史找高频大改文件、单人维护目录（bus factor）与总是一起改的隐性耦合 | 代码热点 `git-hotspots` |

## 输出契约

1. **每条结论附证据**：日志原文行、时间戳、commit 短 hash、变更单号、指标出处。拿不到就写「待确认」。
2. **不下根因结论**：只给按可疑度排序的假设，每条附验证方法与反证，定性由人做。
3. **时间线先于分析**：任何一份产出的第一节都是时间线，缺失的时间点明写「未知」。
4. **人还在故障里就先止损**：先给动作清单与风险提示，深度分析可以晚十分钟。

## 典型组合流程

- **接到告警到发出简报**：日志突变检测定异常起点 → 访问日志统计定影响面 → 变更关联列可疑变更 → 日志时间线重建把多机日志拼成一条 → 线上排查简报出稿 → HTTP 健康巡检确认恢复。
- **日志太多无从下手**：日志模板聚类先降噪，专看最少见的模式 → 挑出新错误关键字 → 日志时间线重建看这类错误的爆发点 → 日志突变检测确认起点是否与某次发布对齐。
- **复盘周**：线上排查简报补齐时间线与改进项 → 代码热点验证出事文件是不是长期高频大改、是不是只有一个人在维护 → 把「补测试 / 拆文件 / 加监控 / 改告警」写成带负责人与截止日的改进项 → 告警规则体检把这次漏报或风暴的规则一并修掉。

## 不做什么

- 不代替人连生产系统执行操作：重启、回滚、改配置、清缓存都由人来按，本技能只给动作清单与风险提示。
- 没有证据就不给根因，也不给「已恢复，可以收工」这类结论。
- 不接触任何未脱敏的内部系统信息；示例一律用 example.com 与 GitHub / GitLab / Jira。
- 不做日常性能调优与容量规划，那是压测与部署类技能的事。
