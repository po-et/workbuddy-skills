# 示例：监控告警推到值班群并 @ 值班人

> 示例对话。服务名、手机号、链接均为虚构；下面的脚本输出是在本机用假接收端真实跑出来的（key 为本地测试值，只显示后 4 位）。

## 对话

**用户**：订单服务下单成功率掉到阈值以下时，想自动推到值班群，@ 当班的人。群机器人已经加好了。

**助手（先问三件事）**：
1. key 请你自己放进环境变量 `WECOM_BOT_KEY`（放 key 或完整地址都行），不要贴到对话里。放好了吗？
2. 要 @ 人就得用 text 类型 + 手机号（markdown 类型不支持 @ 手机号，以官方文档为准）。当班手机号是谁的、怎么拿到？
3. 告警从哪里触发？监控系统能调用一条命令或脚本吗？触发频率大概多高？

**用户**：变量设好了；当班号码先写 13800000000；监控能在告警时执行一条 shell 命令，高峰可能一分钟触发好几次。

## 交付物

**1. 结论**：告警用 text 类型、@ 当班手机号；监控每次触发先经过「去重」，同一指标 10 分钟内只发第一条 [待确认：窗口长度按你们值班习惯调整]；恢复时发一条「已恢复」。第一条消息先预览、你确认后再接入自动发送。

**2. 环境变量检查（不打印值）**

```bash
python3 -c "import os; v=os.environ.get('WECOM_BOT_KEY',''); print('已设置，末 4 位', v[-4:]) if v else print('未设置')"
```

**3. 告警正文 `alert.txt`**

```
【告警】P0 订单服务 下单成功率 异常
现象：下单成功率 = 92.1%（阈值 99%），持续 5 分钟
开始时间：14:05
影响：部分用户下单失败，范围评估中
处理人：请值班同学确认并回复「已接手」
详情：https://example.com/dashboard/order
```

**4. 预览（默认 dry-run，不发送）**

```bash
python3 scripts/wecom_bot_send.py --type text --file alert.txt --at-mobile 13800000000
```


**5. 确认后发送（等你回复「发」再运行）**

```bash
python3 scripts/wecom_bot_send.py --type text --file alert.txt --at-mobile 13800000000 --send
```

同一条命令指向本机假接收端时的实际输出——首个请求被假接收端故意回 503，脚本按规则重试后成功：

```
第 1 次请求失败（HTTP 503），1.0 秒后重试（还可重试 2 次）
结果：errcode=0（成功），共 2 次请求

[fake] #1 POST /cgi-bin/webhook/send key=****7c21 msgtype=text 字节=384 检查=ok → HTTP 503
[fake] #2 POST /cgi-bin/webhook/send key=****7c21 msgtype=text 字节=384 检查=ok → HTTP 200 errcode=0
```

**6. 接入监控时的频率控制**
- 去重：用「服务 + 指标 + 级别」做指纹，窗口内只发第一条；窗口结束如果仍未恢复，发一条「仍在持续，累计 N 次」。
- 恢复：发 `【已恢复】订单服务 下单成功率 已恢复正常，持续 N 分钟。原因：排查中`，不 @ 人。
- 多个指标同时告警：合并成一条列表。
- 官方有频率限制，具体以文档为准；收到 errcode 45009 时脚本不会自动重试，等一个限流窗口后再发，并检查是不是上游在刷告警。

**7. 待确认**
- [待确认] 当班手机号每周轮换时，由谁更新、放在哪个变量或文件里。
- [待确认] 去重窗口 10 分钟是否合适。
- 超时后脚本会重试；超时的请求可能其实已送达，所以告警可能偶尔重复一条——告警场景一般可接受；重要通知用 `--retries 0`。
