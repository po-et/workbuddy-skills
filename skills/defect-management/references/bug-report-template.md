# 缺陷单模板

> 字段名按通用写法给出；在 TAPD 等工具里对应哪个字段、哪些必填，**以你所在项目的 TAPD 配置为准**（项目管理员可以改字段和取值）。

## 一、标题公式

**【模块】在什么条件下 + 做了什么 + 出现什么问题（+ 影响范围）**

| 差 | 好 |
|---|---|
| 支付有问题 | 【支付】iOS 17 使用 Apple Pay 支付成功后，订单仍显示「待支付」（约 3% 订单） |
| 登录报错 | 【登录】连续输错密码 5 次后未触发账号锁定，可继续尝试 |
| 页面很慢 | 【搜索】关键词含 emoji 时搜索结果页加载超过 10 秒后白屏 |

要点：一眼能看出在哪、什么条件、什么现象；不写猜测的原因（「接口有 bug」）；不写情绪（「又崩了！」）。

## 二、正文模板（可直接粘贴）

```
【标题】【模块】条件 + 操作 + 现象（+ 影响范围）

【基本信息】
- 模块：
- 严重度：            （按影响定，见定级规则）
- 优先级：            （由负责人按排期定，提单人可给建议）
- 复现概率：必现 / 偶现（N/10 次）/ 只出现过一次
- 发现版本：
- 环境：测试 / 预发 / 生产
- 设备与系统：        （如 iPhone 15 / iOS 17.x；Chrome 1xx / Windows 11）
- 账号与数据：        （测试账号类型、订单号等；不要写密码）
- 网络：              （Wi-Fi / 4G / 弱网模拟，如相关）

【复现步骤】
1. 前置条件：……
2. ……（每步一个动作，写清点哪里、输入什么）
3. ……

【期望结果】
……（依据：需求文档 / 设计稿 / 线上旧版本行为，写出处）

【实际结果】
……（写现象，不写推测；有报错就原样贴报错文字）

【附件清单】
- [ ] 截图（标出问题位置）
- [ ] 录屏（偶现问题必附）
- [ ] 日志：时间段 HH:MM–HH:MM，关键词：……
- [ ] 请求 ID / traceId：……
- [ ] 抓包或接口返回（先脱敏）

【补充】
- 影响范围：……（多少用户 / 哪些渠道 / 是否有替代路径）
- 初步判断（可选，标「推测」）：……
- 关联单：重复或相关的缺陷编号、需求编号
```

## 三、写复现步骤的规矩

1. 从「干净状态」开始：用哪个账号、在什么页面、缓存清没清。
2. 每步一个动作；输入的数据写具体值（「输入 1001 元」而不是「输入金额」）。
3. 偶现问题写清尝试次数和出现次数，附录屏和出现时刻，方便开发对日志。
4. 只在特定环境出现的，写出对照：「Android 正常，仅 iOS 17 出现」。
5. 写完自己按步骤走一遍；走不通就改到能走通。

## 四、附件脱敏

上传前把手机号、身份证号、银行卡号、密码、令牌（token / cookie / 会话 ID）、客户姓名与地址打码或替换。日志里的令牌尤其容易漏。

## 五、一份写好的缺陷单（示例，内容虚构）

```
【标题】【支付】iOS 17 使用 Apple Pay 支付成功后，订单仍显示「待支付」（约 3% 订单）

【基本信息】
- 模块：支付
- 严重度：严重（已扣款但订单状态错误，用户会重复支付或投诉）
- 优先级建议：P1
- 复现概率：偶现（10 次出现 3 次）
- 发现版本：App 5.2.0（测试包 build 318）
- 环境：测试环境
- 设备与系统：iPhone 15 / iOS 17.5；iPhone 12 / iOS 16 未复现
- 账号与数据：测试账号 A 类（已绑卡）；订单号 T20260902-0041

【复现步骤】
1. 前置条件：登录测试账号，购物车有 1 件商品。
2. 点「去结算」→ 选择 Apple Pay → 确认支付。
3. 支付成功弹窗出现后，点「查看订单」。

【期望结果】
订单状态为「已支付」（依据：支付需求文档 3.2 节）。

【实际结果】
订单状态显示「待支付」；下拉刷新后仍为「待支付」；约 1 分钟后变为「已支付」。

【附件清单】
- [x] 录屏（00:12 处出现问题）
- [x] 日志：10:12–10:15，关键词 payCallback
- [x] 请求 ID：见录屏末尾截图
- [ ] 抓包（待补）

【补充】
- 影响范围：iOS 17 + Apple Pay；其他支付方式未复现。
- 初步判断（推测）：支付回调与订单状态刷新存在时序问题。
- 关联单：无
```
