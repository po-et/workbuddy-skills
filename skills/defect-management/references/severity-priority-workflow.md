# 严重度 × 优先级矩阵、状态流转与重复/无效单处理

> 下面是可直接采用的**建议默认规则**，团队可以按自己的情况调整；字段名与取值（如「致命/严重/一般/提示/建议」还是「S1–S4」）以你所在项目的 TAPD 配置为准。规则定下来后写进团队文档，所有人按同一套口径提单和复盘。

## 一、严重度：看影响，由提单人定

| 严重度 | 判断标准（满足任一条） | 例子 |
|---|---|---|
| 致命 | 核心流程完全不可用；数据丢失或错乱；资金错误；安全漏洞；崩溃且无法恢复 | 优惠券叠加后实付为负数；退款金额错误 |
| 严重 | 核心流程部分失败或结果错误，但有绕过办法；主要功能不可用 | 支付成功后订单状态错误；密码错误多次未锁定 |
| 一般 | 次要功能异常；非核心流程的错误提示、状态不对 | 导出文件乱码；验证码按钮状态不对 |
| 轻微 | 界面、文案、样式问题，不影响使用 | 暗色模式边缘白线；文案错别字 |
| 建议 | 体验优化、易用性建议，不属于缺陷 | 搜索结果为空时希望展示推荐 |

## 二、优先级：看先修谁，由负责人（产品 / 项目负责人）定

| 优先级 | 含义（建议默认） |
|---|---|
| P0 | 立即处理：阻塞发版、线上正在造成损失，需要热修复 |
| P1 | 本迭代必须修复，发版前关闭 |
| P2 | 排进后续迭代 |
| P3 | 有空再修，或转入需求池 |

## 三、矩阵：严重度 × 影响面 → 默认优先级

| 严重度 ＼ 影响面 | 大部分用户或核心路径 | 部分用户或特定条件 | 个别用户或极端条件 |
|---|---|---|---|
| 致命 | P0 | P0 | P1 |
| 严重 | P0 | P1 | P2 |
| 一般 | P1 | P2 | P3 |
| 轻微 | P2 | P3 | P3 |
| 建议 | P3 | P3 | 需求池 |

矩阵给的是默认值，负责人可以上调或下调，但要在单子里写一句理由。典型的「严重度低、优先级高」：支付成功页的错别字（轻微，但在高曝光页面、上线前必须改）；典型的「严重度高、优先级低」：只在已下线的旧版本出现的崩溃。

## 四、状态流转

```
新建 ──确认──▶ 已确认/已指派 ──开始──▶ 处理中 ──修复──▶ 已解决(待验证) ──验证通过──▶ 已关闭
  │                 │                                    │
  │                 └──▶ 挂起/延期（写原因 + 复查日期）      └──验证不通过──▶ 重新打开 ──▶ 处理中
  └──▶ 拒绝（重复 / 无法复现 / 设计如此 / 不修复，须写理由）──提单人确认──▶ 已关闭
```

规则（建议默认）：
1. **谁改状态**：确认与指派——测试负责人或模块负责人；「已解决」——开发；「已关闭」——验证人（通常是提单人或测试）；开发不关自己修的单。
2. **必填**：已解决时填解决方式、修复版本；拒绝时填拒绝类型与理由；挂起时填原因与复查日期；重新打开时写本次验证的环境与现象。
3. **时限**：各优先级的响应与修复时限由团队约定（如 P0 当天响应），写进团队文档；复盘时统计超时的单。
4. **验证**：在修复版本、同一环境按原复现步骤验证；偶现问题至少验证原复现次数。
5. **不跳状态**：不从「新建」直接到「已关闭」，除非是拒绝类并写了理由。

## 五、重复单与无效单

| 类型 | 处理 | 注意 |
|---|---|---|
| 重复 | 关联到原单后关闭；保留信息更完整的那张；把新单的补充信息（新环境、新复现路径）合并到原单 | 先搜索再提单：按模块 + 关键词搜近期的单 |
| 无法复现 | 开发写清在什么环境、按什么步骤没复现；提单人补录屏、日志、数据；约定期限内（团队自定）仍无补充则关闭，再出现时重新打开 | 偶现问题不要轻易判无法复现，先对日志 |
| 设计如此 | 由产品确认并在单里引用需求文档或设计稿；如果确实体验不好，转为需求或建议 | 不要由开发单方面判定 |
| 不修复 | 写明理由（成本、影响极小、即将下线）和风险接受人 | 严重及以上的缺陷不修复，需要负责人签字确认 |

## 六、TAPD 中怎么落地

具体的工作流配置、状态名称、必填字段设置入口，以你所在项目的 TAPD 配置为准，需要项目管理员操作；官方说明去 TAPD 帮助中心查「缺陷」「工作流」「自定义字段」相关章节（章节名以帮助中心当前目录为准）。本技能不代替用户修改任何配置。
