# 每周缺陷复盘：统计口径与会议流程

## 一、统计口径（每周用同一套，才看得出趋势）

| 指标 | 口径 | 脚本字段 / 位置 |
|---|---|---|
| 统计日 | 复盘用的「今天」，写死在报告里（如 2026-09-26），保证能复现 | `--today` |
| 统计区间 | 上周一到上周日，或上次复盘到本次复盘前一天 | `--since` / `--until` |
| 新增 | 创建日期落在区间内的缺陷数 | 一、总体 |
| 关闭 | 关闭日期落在区间内的缺陷数（含无效/重复/拒绝，单独列出）；没有关闭时间列则用解决时间 | 一、总体 |
| 净增 | 新增 − 关闭；连续几周为正说明在积压 | 一、总体 |
| 未关闭存量 | 状态不是「已关闭」也不是「无效/重复/拒绝」的缺陷；「已解决待验证」「挂起」也算未关闭 | 一、总体 |
| 严重度分布 | 全部与未关闭两列；高严重度默认指前两档（如致命、严重），可用 `--high-severity` 改 | 二 |
| 模块分布 | 按模块的总数、占比、未关闭数、未关闭中高严重度数 | 三 |
| 存活天数 | 未关闭缺陷：统计日 − 创建日期，分 0–3 / 4–7 / 8–14 / 15–30 / 31–90 / >90 天 | 五 |
| 解决周期 | 已关闭（不含无效类）缺陷：创建 → 解决日期（没有就用关闭日期），报中位数、平均、P90；按日期计，同日为 0 | 六 |
| 长期未关闭 | 高严重度且存活超过阈值（默认 7 天，`--stale-days` 可改）的清单 | 七 |
| 无效率 | 无效/重复/拒绝 ÷ 总数，反映提单质量或需求理解偏差 | 一、总体 |
| 重开率 | 重开过（重开次数 > 0）÷ 总数，反映修复质量或验证标准 | 一、总体 |

口径注意：
- 导出范围要一致：每周都导出「全部状态」的缺陷，而不是只导出未关闭的，否则关闭数和周期算不出来。
- 重复导出的同一 ID 只算一次（脚本默认去重并在「数据问题」里说明）。
- 状态名和严重度取值不在内置词表里的，脚本会列在「数据问题」里，按实际含义用 `--closed-status`、`--open-status` 等补充后重跑，不要硬算。
- 处理人分布只用来排负载，不用来排名。

## 二、复盘会流程（30 分钟以内）

1. **看趋势（5 分钟）**：新增、关闭、净增、未关闭存量与上周比。
2. **过长期未关闭的高严重度清单（10 分钟）**：每条确认下一步和日期；卡住的写明卡在哪、要谁支持。
3. **看聚集（5 分钟）**：缺陷集中的模块，是需求不清、改动太大还是测试不足？
4. **看质量信号（5 分钟）**：无效率高 → 提单前先搜重、补复现步骤、对齐需求；重开率高 → 修复后自测、明确验证标准。
5. **定行动（5 分钟）**：最多 3 条改进行动，每条有负责人和日期，下周复盘第一件事就是检查这 3 条。

## 三、复盘摘要骨架（发群或发邮件）

```
【缺陷周复盘】<项目> <区间>（统计日 <日期>）
一句话：<本周新增 N、关闭 M、净增 ±K；最需要关注的是 ……>
1. 总体：未关闭 X（高严重度 Y），无效率 A%，重开率 B%
2. 需要关注：存活超过 7 天的高严重度缺陷 Z 个（见清单）
3. 聚集：<模块> 占 C%，<原因判断，标「推测」>
4. 行动（≤3 条）：<行动> —— <负责人>，<日期>
5. 数据问题：<未识别状态、缺创建时间等，已如何处理>
附：脚本完整输出
```
