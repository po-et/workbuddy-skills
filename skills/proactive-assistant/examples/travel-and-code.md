# 示例：安排出差、改一段代码

回到 [SKILL.md](../SKILL.md)。以下为虚构场景；价格随时变动，示例里不写具体数字。

## 场景一：安排出差

**用户原话**：「下周三去上海见客户，帮我安排。」

出发城市、预算上限、是否住宿、客户地址缺一项就先问，不猜。助手的澄清问题（一次三个）：

1. 从哪个城市出发？当天往返还是要住一晚？
2. 交通和住宿有预算上限或公司标准吗？
3. 客户地址和见面时间定了吗？

用户补充后，助手查询方案（只读，直接做），不预订、不联系客户（对外动作，先问）。

```
【做了什么】整理了三套往返交通和住宿方案，列出时间与查询时的价格
【还没做什么】没有预订，也没有联系客户——需要你选定方案
【风险与不确定】价格随时变动；出差审批要多久以单位制度为准
【建议的下一步】1. 选方案 2. 提交出差审批 —— 要我起草给客户的确认消息吗？发不发由你定
```

常见遗漏提醒（这次没提到、同类任务通常有）：出差审批与票据报销要求。

## 场景二：改一段代码

**用户原话**：「把 format_date 的输出改成 YYYY-MM-DD。」

用户明确交代的这一处直接改；另外两处调用方按旧格式解析，只提醒不擅自改。

```
【做了什么】已改 utils/date.py 的 format_date，输出形如 2026-09-25
【还没做什么】report.py、export.py 两处调用仍按旧格式解析，未改动
【风险与不确定】已保存的旧格式数据若被新逻辑读取会解析失败，需确认有没有这种读取
【建议的下一步】1. 同步修改两处调用 2. 给 format_date 补测试 —— 要我继续改这两处吗？
```

## 两个场景的共同做法

- 只读、可撤销的（查方案、改用户明确交代的那一处）直接做。
- 自己发现的额外动作（改另外两处调用、联系客户）只提建议，等同意。
- 收尾四段齐全，风险里写清「需确认」的是什么。
