# ADR 格式

ADR 放在 `docs/adr/`，顺序编号：`0001-slug.md`、`0002-slug.md` ……

`docs/adr/` 目录惰性创建：第一份 ADR 需要时才建。

## 模板

```md
# {决策的短标题}

{1–3 句：背景是什么、我们决定了什么、为什么。}
```

就这些。一份 ADR 可以只有一段话。价值在于记录**做过**这个决策以及**为什么**，不在于填满各个章节。

## 可选章节

只在确实有价值时加。多数 ADR 不需要。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决策会被重新审视时有用
- **考虑过的方案**：只有被否的备选值得记住时
- **后果**：只有非显而易见的下游影响需要点明时

## 编号

扫描 `docs/adr/` 取最大编号加一。

## 什么时候提议 ADR

三条必须同时成立：
1. **难以逆转**：以后改主意代价不小
2. **没有上下文会令人费解**：未来的读者看代码会想「到底为什么这么做？」
3. **真实权衡的结果**：确有备选方案，你出于具体原因选了这个

容易逆转的决策跳过：以后直接改就是了。不令人费解的没人会问为什么。没有真正备选的，除了「我们做了显然的事」没什么可记。

### 哪些够格

- **架构形态。**「我们用 monorepo。」「写模型事件溯源，读模型投影到 Postgres。」
- **上下文之间的集成模式。**「订单与账单通过领域事件通信，不走同步 HTTP。」
- **带锁定效应的技术选型。** 数据库、消息总线、认证提供方、部署目标。不是每个库都算，只有换掉要花一个季度的那些。
- **边界与范围决策。**「客户数据由 Customer 上下文拥有；其他上下文只按 ID 引用。」明确的「不做」和「做」一样有价值。
- **对显然路径的刻意偏离。**「我们手写 SQL 而不用 ORM，因为 X。」任何理性读者会假设相反的地方。这能阻止下一位工程师把刻意的东西「修掉」。
- **代码里看不见的约束。**「因合规要求不能用某云厂商。」「因合作方 API 契约，响应必须在 200ms 内。」
- **拒绝的非显然备选。** 你考虑过 GraphQL 却出于微妙原因选了 REST，记下来；否则六个月后有人又会提 GraphQL。
