# Bug 诊断法

对付疑难 Bug 与性能回退的一套纪律。**只有明确说明理由才能跳过某个阶段。**
线上正在冒烟、需要先出简报稳住局面时，先用「线上排查简报」技能整理时间线，再回到这里找根因。

## 脱敏

本技能会让你展示命令、输出与抓取的产物。**先脱敏再展示**：凭证一律写成 `<REDACTED>`；构造回路时从环境变量读凭证，让密钥留在环境里而不是出现在你贴出来的内容里；抓包/日志只引用带信号的那几行。脱敏后信息不够就直说，问用户要。

## 阶段 1：造一个反馈回路（这就是本技能的全部）

其余阶段都是机械的。只要有一个**紧凑的、能对这个 bug 变红**的通过/失败信号，二分、假设检验、加探针都只是在消费它；没有信号，盯代码盯到天亮也没用。在这里投入不成比例的精力，**激进、有创造力、拒绝放弃**。

构造方式，大致按此顺序尝试：

1. **失败测试**：在能触达 bug 的最近一层（单元 / 集成 / e2e）。
2. **curl / HTTP 脚本**打本地服务。
3. **CLI + 固定输入**，把 stdout 与已知正确快照 diff。
4. **无头浏览器脚本**（Playwright）驱动 UI，断言 DOM / console / 网络。
5. **回放真实产物**：把线上请求 / 事件日志存盘，单独回放这条代码路径。
6. **一次性小环境**：只起一个服务、mock 依赖，一个函数调用打到 bug 路径。
7. **属性 / 模糊循环**："偶尔输出错"就跑 1000 个随机输入找失败模式。
8. **二分脚本**：bug 出现在两个已知状态之间（提交、数据集、版本）就自动化"切到 X → 检查 → 重复"，交给 `git bisect run`。
9. **差分回路**：同一输入过旧版 / 新版（或两套配置），diff 输出。
10. **人肉回路（最后手段）**：必须有人点的，用一个结构化脚本指挥人：打印步骤 → 等输入 → 记录结果，让输出仍能回流给你。

**把回路当产品打磨**：更快（缓存初始化、缩小范围）、信号更尖（断言具体症状而不是"没崩"）、更确定（固定时间、随机种子、隔离文件系统与网络）。30 秒的抖动回路比没有好不了多少；2 秒的确定回路是超能力。

**非确定性 bug**：目标不是干净复现，是**提高复现率**。循环 100 次、并行、加压、缩小时间窗、插 sleep。50% 复现率能查，1% 不能——把它抬到能查为止。

**真的造不出回路**：明确停下来说，列出试过什么，向用户要：(a) 能复现的环境；(b) 脱敏后的抓取产物（HAR、日志、core dump、带时间戳的录屏）；(c) 允许加临时线上探针。**没有回路不进入假设阶段。**

**完成标准**：你能说出**一条命令**（脚本 / 测试 / curl），并且**已经至少跑过一次**（贴出命令与脱敏输出），它满足：
- [ ] 能变红：驱动真实 bug 路径并断言**用户描述的那个症状**；修好后会变绿。
- [ ] 确定：每次跑结论一致（偶现 bug 则复现率已固定在可查水平）。
- [ ] 快：秒级。
- [ ] 无人值守可跑。

发现自己在没有这条命令前就读代码建理论——**停**，这正是本技能要防的失败。

## 阶段 2：复现 + 最小化

跑回路，看它变红。确认：是**用户描述的那个**失败而不是旁边另一个；多次可复现；已记录精确症状（报错文本、错误输出、耗时）。
然后**最小化**：逐一删输入、调用方、配置、数据、步骤，每删一项重跑，只保留"删了就变绿"的部分。最小复现缩小假设空间，也是阶段 5 的回归测试。

## 阶段 3：假设

先列 **3–5 个按可能性排序的假设**再验证任何一个——只想一个会锚定在第一个"像"的念头上。每个假设必须**可证伪**：

> "如果原因是 X，那么改 Y 会让 bug 消失 / 改 Z 会让它更严重。"

说不出预测的假设是感觉，丢掉或磨尖。**验证前把排序给用户看**：他们常有领域知识能瞬间重排（"我们刚发了 #3 相关的改动"）。用户不在也不阻塞，按你的排序继续。

## 阶段 4：探针

每个探针对应阶段 3 的一个具体预测，**一次只改一个变量**。优先级：调试器 / REPL 断点 > 边界处的定向日志 > 绝不"全打日志再 grep"。
所有调试日志加唯一前缀如 `[DEBUG-a4f2]`，清理时一条 grep 搞定。
**性能回退分支**：日志通常是错的工具。先建基线测量（计时脚本、profiler、执行计划），再二分。先测量后修。

## 阶段 5：修复 + 回归测试

**先写回归测试再修**，前提是存在**正确的缝**：测试要在 bug 真实发生的调用点重现它。缝太浅（需要多个调用方而单元测试只有一个）就会给假信心。
**没有正确的缝本身就是发现**：记下来，架构在阻止 bug 被锁定。
有缝就：最小复现改成失败测试 → 看它失败 → 修 → 看它通过 → 用阶段 1 的回路跑原始（未最小化）场景。

## 阶段 6：清理

- [ ] 原始复现不再复现（重跑阶段 1 回路）
- [ ] 回归测试通过（或已记录"无缝"）
- [ ] 所有 `[DEBUG-…]` 探针已删（grep 前缀）
- [ ] 一次性原型已删或移到明确标记的 debug 目录
- [ ] 提交信息里写明最终成立的假设，让下一个人少走弯路
