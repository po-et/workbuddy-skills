# 不做清单知识库（`.out-of-scope/`）

仓库里的 `.out-of-scope/` 目录持久记录被拒绝的功能请求。两个用途：

1. **组织记忆**：功能为什么被拒，工单关闭后理由不会丢
2. **去重**：新工单和既往拒绝匹配时，技能能翻出旧决策，而不是重新吵一遍

## 目录结构

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

一个文件对应一个**概念**，不是一个工单。多个工单要同一个东西，归到一个文件下。

## 文件格式

用放松、可读的风格写，更像一份短设计文档而不是数据库记录。用段落、代码示例和例子把理由讲清楚，让第一次看到的人也能理解、能用。

```markdown
# 深色模式

本项目不支持深色模式或面向用户的主题化。

## 为什么不做

渲染管线假设 `ThemeConfig` 里定义的单一调色板。支持多主题需要：

- 包住整个组件树的主题 context provider
- 每个组件的主题感知样式解析
- 用户主题偏好的持久层

这是一次重大架构改动，与项目专注内容创作的定位不符。主题化是嵌入或再分发输出的下游使用者的事。

```ts
// 当前 ThemeConfig 接口并非为运行时切换设计：
interface ThemeConfig {
  colors: ColorPalette; // 单一调色板，构建期解析
  fonts: FontStack;
}
```

## 既往请求

- #42：「增加深色模式」
- #87：「无障碍夜间主题」
- #134：「深色主题选项」
```

### 文件命名

用简短、描述性的 kebab-case 概念名：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名字要让人浏览目录时不打开文件也知道拒的是什么。

### 写理由

理由要有实质：不是「我们不想要」，而是为什么。好的理由引用：
- 项目范围或理念（「本项目专注 X；主题化是下游的事」）
- 技术约束（「支持它需要 Y，与我们的 Z 架构冲突」）
- 战略决策（「我们选 A 而不是 B，因为……」）

理由要耐久。避免引用临时情况（「我们现在太忙」）；那不是拒绝，是推迟。

## 什么时候查 `.out-of-scope/`

分诊时（第 1 步：收集上下文）读取 `.out-of-scope/` 下所有文件。评估新工单时：
- 检查请求是否匹配已有的不做概念
- 按概念相似度匹配，不是关键词：「夜间主题」匹配 `dark-mode.md`
- 匹配上了就告诉维护者：「这和 `.out-of-scope/dark-mode.md` 相似。之前拒绝的理由是 [理由]。你现在还这么想吗？」

维护者可以：
- **确认**：新工单追加到已有文件的「既往请求」，然后关闭
- **重新考虑**：删除或更新不做文件，工单走正常分诊
- **不同意**：相关但不同，走正常分诊

## 什么时候写 `.out-of-scope/`

只在**需求**（不是 bug）被以 `wontfix` *拒绝* 时。需求类 PR 同理：被拒的 PR 也记在这里，免得同一个请求换成代码又回来。

**不要**在因为「已经实现了」而以 `wontfix` 关闭时写入。那是建成的功能，不是被拒的；记进来会用假拒绝污染去重检查。此时关闭评论指向功能已存在的位置即可。

流程：
1. 维护者决定某功能请求不在范围内
2. 检查是否已有匹配的 `.out-of-scope/` 文件
3. 有：把新工单追加到「既往请求」
4. 没有：新建文件，写概念名、决策、理由和第一条既往请求
5. 在工单上评论说明决策，提及该 `.out-of-scope/` 文件
6. 打 `wontfix` 标签关闭

## 更新或移除

维护者对之前拒绝的概念改主意了：
- 删除该 `.out-of-scope/` 文件
- 技能不需要重开旧工单；它们是历史记录
- 触发重新考虑的新工单走正常分诊
