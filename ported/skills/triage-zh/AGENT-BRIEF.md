# 写 Agent 简报

Agent 简报是工单进入 `ready-for-agent` 时贴在 Issue 或 PR 上的一条结构化评论。它是离线 Agent 据以工作的**权威规格**：原始正文和讨论只是背景，简报才是契约。

简报说的是**Agent 该做什么**。对 Issue，是从零建出这个改动；对 PR，是对**现有 diff** 还要做什么：收尾、补缺、处理评审意见。原则一样，下面的 PR 示例展示差别。

## 原则

### 耐久优先于精确

工单可能在 `ready-for-agent` 里躺几天甚至几周，其间代码库会变。简报要写成文件改名、移动、重构之后仍然有用的样子。

- **要**描述接口、类型、行为契约
- **要**点名 Agent 该找或该改的具体类型、函数签名、配置形状
- **不要**引用文件路径：会过期
- **不要**引用行号
- **不要**假设当前实现结构不变

### 写行为，不写步骤

描述系统**应该做什么**，不是**怎么实现**。Agent 会重新探索代码库，自己做实现决策。

- **好：**「`SkillConfig` 类型应接受可选的 `schedule` 字段，类型为 `CronExpression`」
- **差：**「打开 src/types/skill.ts，在第 42 行加一个 schedule 字段」
- **好：**「用户不带参数运行 `/triage` 时，应看到需要关注的工单摘要」
- **差：**「在主处理函数里加一个 switch」

### 完整的验收标准

Agent 得知道什么时候算做完。每份简报必须有具体、可测试的验收标准，每条能独立验证。

- **好：**「运行 `gh issue list --label needs-triage` 返回已经过初步分类的工单」
- **差：**「分诊应该正常工作」

### 明确的范围边界

写清什么不在范围内，防止 Agent 镀金或对相邻功能做假设。

## 模板

```markdown
## Agent 简报

**类别：** bug / enhancement
**摘要：** 一句话说明需要发生什么

**当前行为：**
描述现在发生什么。bug 就是坏掉的行为；需求就是这个功能要建立在其上的现状。

**期望行为：**
描述 Agent 完成后应该发生什么。边界情况和错误条件要具体。

**关键接口：**
- `TypeName`：要改什么、为什么
- `functionName()` 返回类型：现在返回什么 vs 应该返回什么
- 配置形状：需要哪些新配置项

**验收标准：**
- [ ] 具体、可测试的标准 1
- [ ] 具体、可测试的标准 2
- [ ] 具体、可测试的标准 3

**不在范围内：**
- 本工单不应改动或处理的东西
- 看似相关但独立的相邻功能
```

## 示例

### 好的简报（bug）

```markdown
## Agent 简报

**类别：** bug
**摘要：** 技能描述截断在单词中间切断，产生坏输出

**当前行为：**
技能描述超过 1024 字符时，在第 1024 个字符处硬截断，不管词边界，导致描述以半个词结尾（如 "Use when the user wants to confi"）。

**期望行为：**
截断应在 1024 字符前的最后一个词边界断开，并追加 "..." 表示截断。

**关键接口：**
- `SkillMetadata` 类型的 `description` 字段：类型不变，但填充它的校验/处理逻辑要尊重词边界
- 任何读取 SKILL.md frontmatter 并提取 description 的函数

**验收标准：**
- [ ] 1024 字符以内的描述不变
- [ ] 超过 1024 的描述在 1024 前最后一个词边界截断
- [ ] 截断后的描述以 "..." 结尾
- [ ] 含 "..." 的总长度不超过 1024

**不在范围内：**
- 修改 1024 这个上限本身
- 多行描述支持
```

### 好的简报（需求）

```markdown
## Agent 简报

**类别：** enhancement
**摘要：** 增加 `.out-of-scope/` 目录支持，用于记录被拒绝的功能请求

**当前行为：**
功能请求被拒时，工单打上 `wontfix` 关闭并留评论。决策和理由没有持久记录，以后类似请求要靠维护者回忆或翻旧讨论。

**期望行为：**
被拒的功能请求记录到 `.out-of-scope/<concept>.md`，包含决策、理由和所有提出过该功能的工单链接。分诊新工单时检查这些文件是否匹配。

**关键接口：**
- `.out-of-scope/` 的 Markdown 格式：每个文件有 `# 概念名` 标题、`**决策：**` 行、`**原因：**` 行、`**既往请求：**` 列表（含工单链接）
- 分诊流程应尽早读取所有 `.out-of-scope/*.md`，按概念相似度匹配新工单

**验收标准：**
- [ ] 以 wontfix 关闭功能请求时创建/更新 `.out-of-scope/` 里的文件
- [ ] 文件包含决策、理由和被关闭工单的链接
- [ ] 已有匹配文件时，新工单追加到其「既往请求」列表而不是新建
- [ ] 分诊时检查现有 `.out-of-scope/` 文件，新工单匹配既往拒绝时予以提示

**不在范围内：**
- 自动匹配（由人确认匹配）
- 重新开放已拒绝的功能
- bug 报告（只有需求类拒绝进 `.out-of-scope/`）
```

### 好的简报（PR）

PR 场景下，「当前行为」描述 diff 的状态，简报要求 Agent 收尾或修正，而不是从零开始。

```markdown
## Agent 简报

**类别：** enhancement
**摘要：** 把贡献者给 `triage list` 加的 `--json` 输出标志做完

**当前行为：**
PR 加了 `--json` 标志，把工单列表序列化成 JSON。主路径能工作，diff 也符合项目的命令结构。还差两处：错误仍以人类可读文本输出（不是 JSON），新标志没有测试覆盖。

**期望行为：**
带 `--json` 时，所有输出（含错误）都是 stdout 上的合法 JSON，命令退出码不变。不带该标志时现有的人类可读输出不受影响。

**关键接口：**
- 命令的错误路径在 `--json` 下应输出 `{ "error": string }` 而不是纯文本
- 复用 PR 已加的序列化器，不要引入第二个

**验收标准：**
- [ ] `triage list --json` 在成功与错误两种情况下都输出合法 JSON
- [ ] 退出码与非 JSON 命令一致
- [ ] 测试覆盖 `--json` 的成功输出和一个错误用例
- [ ] 默认（非 JSON）输出逐字节不变

**不在范围内：**
- 给其他命令加 `--json`
- 改变 PR 已定义的成功载荷 JSON 形状
```

### 差的简报

```markdown
## Agent 简报

**摘要：** 修一下分诊的 bug

**要做的事：**
分诊那块坏了。看看主文件修一下。第 150 行附近的函数有问题。

**要改的文件：**
- src/triage/handler.ts（第 150 行）
- src/types.ts（第 42 行）
```

差在：没有类别；描述含糊（「分诊那块坏了」）；引用了会过期的文件路径和行号；没有验收标准；没有范围边界；没有当前 vs 期望行为的描述。
