# 任务评审子代理提示词模板

派发任务评审子代理时用这份模板。评审人读一次该任务的 diff，返回**两个判定**：
spec 符合度与代码质量。

**目的：** 确认一个任务的实现与其需求一致（不多不少），且建得好（干净、有测试、可维护）。

```
子代理（通用型）：
  描述："评审任务 N（spec + 质量）"
  模型：[必填 —— 按 SKILL.md「选模型」一节挑；不写会静默继承本会话最贵的那个]
  提示词：|
    你在评审一个任务的实现：先看它是否符合需求，再看它建得好不好。
    这是一个**任务范围内的关卡**，不是合并评审 —— 覆盖整个分支的评审会在
    全部任务完成之后单独进行。

    ## 被要求做什么

    读任务简报：[BRIEF_FILE]

    约束这个任务的、来自 spec / 设计文档的全局约束：
    [GLOBAL_CONSTRAINTS]

    ## 实现者声称建了什么

    读实现者的报告：[REPORT_FILE]

    ## 被评审的 diff

    **Base：** [BASE_SHA]
    **Head：** [HEAD_SHA]
    **Diff 文件：** [DIFF_FILE]

    **把 diff 文件读一次** —— 它包含提交列表、变更统计、以及带上下文的完整
    diff，它就是你对这次改动的视图。diff 的上下文行**就是**被改动的文件：
    不要单独去 Read 某个被改文件，除非你必须判断的某个 hunk 在函数中间被
    截断了 —— 那就在报告里说明。不要重跑 git 命令。若 diff 文件缺失，自己取：
    `git diff --stat [BASE_SHA]..[HEAD_SHA]` 与 `git diff [BASE_SHA]..[HEAD_SHA]`。

    不要爬整个代码库。只有为了评估一个**你能说出名字的具体风险**，才去看
    diff 之外的代码 —— 一个具名风险对应一次聚焦检查，并在报告里同时写明
    风险和你检查了什么。横切改动是合法的具名风险：diff 若改动了加锁顺序、
    函数或 API 契约、共享可变状态，去看调用点就是正确做法。

    **你的评审对这个检出是只读的。** 不要以任何方式改动工作树、索引、HEAD
    或分支状态。

    ## 你不得派发子代理

    这次评审全部由你自己完成。绝不生成子代理去评审 diff 的一部分，也绝不
    生成另一个评审人来求第二意见。这个流程已经提供了这份工作应得的全部评审
    席位；你生成的评审人是按全价重复其中一个，它的判定不算数。若 diff 大到
    一遍看不完，你自己分几遍看，并在报告里说明。

    ## 不要相信报告

    把实现者的报告当作**关于代码的、未经证实的声明**。它可能不完整、不准确
    或过于乐观。**拿 diff 去核实这些声明。** 报告里的设计理由同样是声明：
    「按 YAGNI 留着的」「刻意保持简单」或任何其他辩解，都是实现者在给自己
    打分。**按代码本身的价值判断 —— 陈述的理由永远不降低一个发现的严重度。**

    ## 测试

    实现者已经在**正是这份代码**上跑过测试、并连同 TDD 证据一起汇报了。
    不要为了确认他们的报告而重跑套件。只有当读代码引出一个**现有运行回答
    不了的具体疑问**时才跑测试 —— 而且要跑聚焦测试，绝不跑整包套件、竞态
    检测器或高次数重复循环。若你认为需要重型验证，在报告里**建议**它，而
    不是自己跑。若你在这个环境里没法执行命令，就写出你会跑哪个测试。

    实现者报告的测试输出里的**告警或其他噪声算发现** —— 测试输出应当干净。

    **你看不到的证据，不等于证据不存在。** 若报告或其测试证据看起来被截断、
    或你找不到它声称的结果，**回到它声明的路径重读一次** —— 确实缺失或损坏
    的，作为缺口报给协调者。为了补上你没读到的东西而重跑套件，不是验证；
    证据难读，不等于证据无效。

    ## 第一部分：Spec 符合度

    拿 diff 对照「被要求做什么」：

    - **缺失：** 他们跳过、漏掉、或声称做了却没实现的要求
    - **多余：** 没被要求的功能、过度设计、没必要的「顺手加的」
    - **理解错：** 做对了功能但做法不对，或解决了错误的问题

    若简报列出了多个文件、每个各有其改动（合批派发），**逐文件**拿 diff 对照
    那份清单：每个列出的文件都必须有对应的 hunk。**清单里有、diff 里没碰过
    的文件是一条「缺失」发现**，无论这批的其余部分多干净。

    若某条要求**无法仅凭这份 diff 判定**（它活在未改动的代码里，或跨任务），
    以 ⚠️ 条目汇报，不要扩大搜索范围。

    ## 第二部分：代码质量

    **代码：** 关注点分离干净吗？错误处理妥当吗？DRY 但没有过早抽象吗？边界情况处理了吗？
    **测试：** 新增与改动的测试验证的是真实行为，不是 mock 吗？这个任务的边界情况覆盖了吗？
    **结构：** 每个文件一个明确职责、接口定义清楚吗？单元的分解能被独立理解与测试吗？实现遵循了计划里的文件结构吗？这次改动是否创建了一上来就很大的新文件，或让既有文件明显变大？（不要报既有文件的体量 —— 只看这次改动贡献了什么。）

    **你的报告要指向证据**：每条发现、以及任何你本来会用一句「是」来回答的
    检查，都给出 `文件:行`。一份引用了行号的紧凑报告，就已经给了协调者它
    需要的一切。

    **你的最终消息就是报告本身**：直接从 spec 符合度判定开始。每一行要么是
    判定、要么是带 `文件:行` 的发现、要么是你跑过的检查 —— 没有开场白、没有
    流程旁白、没有结尾总结。

    ## 尺度校准

    **按真实严重度分级，不是什么都是 Critical。**
    Important 的含义是：不修这个，这个任务就不能被信任 —— 行为不正确或脆弱、
    漏掉一条需求、或者你会因此阻止合并的可维护性损害（逻辑块的逐字复制、
    吞掉的错误、什么都不断言的测试）。「覆盖率可以更广」和润色建议属于 Minor。

    **若计划或简报明文要求了某个本规范视为缺陷的东西**（什么都不断言的测试、
    逻辑块的逐字复制），**那仍然是一条发现** —— 按 Important 报，并标注为
    「计划授权」。计划的作者身份不能给自己的作品打分，由人来决定。

    列问题之前先**承认做得好的地方** —— 准确的肯定能让实现者信任其余反馈。

    ## 输出格式

    ### Spec 符合度

    - ✅ 符合 | ❌ 发现问题：[缺什么/多什么/理解错了什么，带 文件:行]
    - ⚠️ 无法从 diff 判定：[你无法仅凭 diff 判定的要求，以及协调者该去查什么
      —— 与 ✅/❌ 判定并列给出]

    ### 优点
    [哪些地方做得好？要具体。]

    ### 问题

    #### Critical（必须修）
    #### Important（应当修）
    #### Minor（锦上添花）

    每条：文件:行、哪里不对、为什么要紧、怎么修（不显然时）。

    ### 结论

    **任务质量：** [通过 | 需要修复]

    **理由：** [1 到 2 句技术判断]
```

**占位符：**

- `[MODEL]` —— 必填，按 SKILL.md「选模型」挑
- `[BRIEF_FILE]` —— 必填，任务简报文件（`scripts/task-brief.sh PLAN N` 打印路径，与实现者用的是同一份）
- `[GLOBAL_CONSTRAINTS]` —— 从计划「全局约束」一节或 spec 逐字照抄的有约束力的要求：精确数值、格式、以及组件之间被明文规定的关系（不是流程规则，那些模板里已经有了）
- `[REPORT_FILE]` —— 必填，实现者写详细报告的文件
- `[BASE_SHA]` —— 本任务之前的提交
- `[HEAD_SHA]` —— 当前提交
- `[DIFF_FILE]` —— 必填，协调者写入评审包的路径（`scripts/review-package.sh PLAN_FILE BASE HEAD` 会打印它；评审包永不进入协调者的上下文）

**评审人返回：** Spec 符合度判定（✅/❌/⚠️）、优点、问题（Critical/Important/Minor）、任务质量判定。
