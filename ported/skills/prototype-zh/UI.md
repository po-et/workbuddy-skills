# UI 原型

在同一路由上生成**几个结构迥异的 UI 方案**，用浮动底栏切换。用户在浏览器里翻着看，选一个（或从各个里偷零件），其余扔掉。

问题是关于逻辑/状态而不是长什么样，就是错的分支，去 [LOGIC.md](LOGIC.md)。

## 什么时候是对的形状

- 「这个页面应该长什么样？」
- 「我想先看几个仪表盘方案再定。」
- 「设置页试个不同布局。」
- 任何用户本来要花一天在脑子里的三张模糊草图之间纠结的时候。

## 两种子形态：强烈优先 A

UI 原型**贴着应用其余部分**（真实页头、真实侧栏、真实数据、真实密度）时好判断得多。孤零零的一次性路由是真空：每个方案单看都还行。只要有一个合理的现有页面能容纳这些方案，默认用 A。只有原型确实没有近处的家时才用 B。

### 子形态 A：对现有页面的调整（优先）

路由已经存在。方案渲染在**同一路由**上，由 `?variant=` URL 参数门控。现有的数据获取、参数、鉴权全部保留，只换渲染。这是默认；除非有具体理由否则就选它。

原型的对象还没有页面、但*自然会住在某个页面里*（仪表盘的新区块、设置页的新卡片、现有流程的新一步），仍然是 A。把方案挂进宿主页面。

### 子形态 B：新页面（最后手段）

只在被原型的东西确实没有现成页面可住时用（全新的顶层界面，或无处可嵌的流程）。

按项目现有路由约定建一个**一次性路由**。不发明新的顶层结构。命名要一眼看出是原型（路径或文件名里带 `prototype`）。同样的 `?variant=` 模式。

选 B 之前自查：真的没有现成页面能嵌吗？空路由会藏住有内容的页面才暴露的设计问题。

两种子形态的浮动底栏一样。

## 流程

### 1. 写下问题、定 N

默认 **3 个方案**。超过 5 个就不再是「迥异」而是噪音，上限 5。

在原型所在位置或文件顶部注释里用一行写下计划：

> 「设置页三个方案，通过 `?variant=` 切换，挂在现有 `/settings` 路由上。」

不管用户在不在场反驳都有用。

### 2. 生成迥异方案

草拟每个方案。每个都要满足：
- 页面的目的和它能拿到的数据。
- 项目的组件库/样式体系（TailwindCSS、shadcn、MUI、纯 CSS，随项目）。
- 清晰的导出组件名，如 `VariantA`、`VariantB`、`VariantC`。

方案必须**结构上不同**：不同布局、不同信息层级、不同主操作，不只是换颜色。三个微调过的卡片网格不是 UI 原型，是壁纸。两个草稿太像，就带着「不要用卡片网格」的明确指令重做一个。

### 3. 接在一起

在路由上建一个切换组件：

```tsx
// 伪代码，按项目框架改
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：现有数据获取全部保留在切换器之上，只有渲染子树按方案变。

子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂同样的切换器。

### 4. 做浮动切换条

屏幕底部居中一个小的固定定位条，三部分：
- **左箭头**：切到上一个方案（循环）。
- **方案标签**：显示当前方案键，方案导出了名字就一起显示，如 `B（侧栏布局）`。
- **右箭头**：切到下一个（循环）。

行为：
- 点箭头更新 URL 参数（用框架的路由，如 Next 的 `router.replace`、React Router 的 `navigate`），方案可分享、刷新不丢。
- 键盘：`←` `→` 也能切。`<input>`、`<textarea>`、`[contenteditable]` 聚焦时不拦截方向键。
- 视觉上与页面区分（高对比药丸、淡阴影），一眼看出不属于被评估的设计。
- 生产构建隐藏：以 `process.env.NODE_ENV !== 'production'` 或等价检查门控，误合并的原型不会把切换条带给用户。

切换器做成一个共享组件，两种子形态复用。放在项目共享 UI 所在处。

### 5. 交出去

给出 URL（和 `?variant=` 的键）。用户有空就翻。有趣的反馈通常是**「我要 B 的页头配 C 的侧栏」**——那才是他们真正想要的设计。

### 6. 归档结论并清理

某个方案胜出后，记录答案（哪个、为什么），再按 [SKILL](SKILL.md) 归档原型。把赢家并入真实代码，其余移到一次性分支，不留在 main：
- **子形态 A**：赢家并入现有页面；落选方案和切换器从 main 删掉。
- **子形态 B**：赢家提升为真实路由；一次性路由和切换器从 main 删掉。

完整的方案集是一手资料，所以进一次性分支而不是垃圾桶——留在 main 里的方案组件和切换器烂得很快，还会迷惑下一个读者。

## 反模式

- **只在颜色或文案上不同的方案。** 那是微调，不是原型。真正的方案在结构上有分歧。
- **方案之间共享太多代码。** 共享 `<Header>` 可以；共享 `<Layout>` 就毁掉了意义。每个方案应能自由推翻布局。
- **把方案接到真实写操作上。** 只读原型没问题。方案需要写就指向桩：问题是「应该长什么样」，不是「后端能不能用」。
- **把原型直接提升到生产。** 方案代码是在原型约束下写的（无测试、最少错误处理）。并入时要正经重写。
