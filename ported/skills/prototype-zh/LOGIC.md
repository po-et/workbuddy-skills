# 逻辑原型

一个自包含的单文件 HTML（**可分享的演示**），任何人点按钮就能驱动一个状态模型。用在问题关于**业务逻辑、状态流转或数据形状**的时候：纸面上看着合理、推过真实用例才发现不对的那种东西。

因为是一个文件、无需安装，可以直接交给非开发者（设计师、产品经理、领域专家）让他们自己感受这个模型。所以它说的是他们的语言，不是代码的语言。

## 什么时候是对的形状

- 「我不确定这个状态机能不能处理先 X 后 Y 的边界。」
- 「这个数据模型真的能表示……的情况吗？」
- 「写 API 之前我想先摸一摸它该长什么样。」
- 任何有人想**按按钮看状态变化**的时候。

问题是「这应该长什么样」，就是错的分支，去 [UI.md](UI.md)。

## 流程

### 1. 写下问题

写代码之前，先写下要原型的是什么状态模型、要回答什么问题。一段话，放在演示顶部（可见的引言，不只是注释）。回答错问题的逻辑原型纯属浪费，所以把问题显式写出来，事后能核对——不管用户此刻在不在看。

### 2. 把逻辑隔离成可移植模块

真正的逻辑（回答问题的那部分）放在一个 `<script>` 块里，写成一个小而纯的模块，将来可以原样抬出来放进真实代码库。外面的页面是一次性的，这个模块不是。

形状取决于问题：
- **纯 reducer**：`(state, action) => state`。动作是离散事件、状态是单一值时合适。
- **状态机**：显式的状态与流转。「此刻哪些动作是合法的」本身就是问题时合适。
- **一小组纯函数**作用于普通数据类型。没有隐式当前状态、只有变换时合适。
- **带清晰方法面的类或模块**，逻辑确实拥有持续内部状态时。

按最贴合问题的形状选，*不是*按最容易接到页面上的选。保持纯：没有 DOM、没有 `document`、没有按钮回调伸进来。页面调用它，反向不流动。这就是原型在自身寿命之后仍然有用的原因：问题一答完，验证过的 reducer / 状态机 / 函数组可以直接抬进真实模块。

### 3. 做可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS：无框架、无打包、无服务器，全部内联，双击就开、被邮件转来转去也不坏。任何人打开就能跑。

为非开发者写。每个标签用**领域语言**，不用代码：按钮和状态读起来像业务，不像 reducer。用大白话解释正在发生什么。

自上而下的清晰层级：
1. **标题与一句话说明**这个演示让你探索什么（第 1 步的问题）。
2. **当前状态**：完整的相关状态，渲染成可读面板（带标签的字段，不是原始 JSON 倾倒），每次点击后重渲染让变化可见。对非开发者有帮助的地方，标出刚才变了什么。
3. **自由按钮**：每个动作一个按钮，始终可用，任何人可以任意顺序戳这个模型。每次点击派发动作并重渲染状态。
4. **引导剧本**：一组**场景**，每个一个标签页。每页有该场景的简短大白话描述（它设置的情境、该观察什么），下面是该场景**要按的按钮**，按顺序排列。每一步都是真按钮：点击执行该动作并推进到下一步。开始一个剧本会重置到已知初始状态，保证每次跑法一样。

选能演示别扭情况的场景，就是纸面上难推理的那些：主路径、一个棘手的边界、一次本该非法的尝试。

保持好看但克制：干净的排版、宽松的间距、一种强调色。没有动画、没有花活：不能有任何东西与状态和按钮争夺注意力。

### 4. 交出去

把文件发给他们或替他们打开。他们有空就会点剧本、自由玩；有趣的时刻是他们说「等等，这不应该可能」或「咦，我以为 X 会不一样」——那是*想法*里的 bug，正是整件事的意义。想加新动作或新场景就加。原型会演化。

### 5. 归档结论与原型

原型回答完它的问题后，先记录答案，再按 [SKILL](SKILL.md) 描述的方式归档原型。逻辑分支的具体映射：验证过的 reducer / 状态机 / 函数组抬进真实模块（被吸收的决策）；HTML 外壳随原型一起进一次性分支作为一手资料——因为是单个自包含文件，在那里随时可以重新运行。

## 反模式

- **别加测试。** 需要测试的原型已经不是原型。
- **别接真实数据库。** 用内存状态，除非问题就是关于持久化。
- **别泛化。** 没有「万一以后要支持 X」。原型只回答一个问题。
- **别把逻辑和页面糊在一起。** 纯模块引用了 DOM、`document` 或按钮回调，就抬不出来了。页面只是纯模块外面的薄壳。
- **别上框架、打包器或服务器。** 一个收件人双击就开的文件；React 应用或开发服务器会毁掉「可分享」。
- **别把 HTML 外壳发到生产。** 页面是为手动点击优化的。背后的逻辑模块才是值得留的部分。
