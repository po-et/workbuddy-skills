# 工具设计最佳实践

## 工具哲学

工具是 Agent 与世界的主要接口。传统 API 面向理解底层系统的开发者；工具面向从描述推断意图、从自然语言生成调用的语言模型。目标是让 Agent 不经大量试错就能发现、理解、正确使用工具。定义里的每个歧义都是潜在失败模式，每个不清晰的参数名逼 Agent 猜，每个缺失的示例让边界情况无所依据。

## 描述工程原则

**原则 1：回答根本问题。** 做什么（具体到位，不用「有助于」）；何时用（直接触发 + 间接信号）；接受什么输入（类型、约束、默认值、各参数控制什么）；返回什么（输出格式与结构、成功示例、错误条件）。

**原则 2：结构一致。** 全部工具用同一结构，Agent 从别的工具学到的模式能预测在哪找信息。推荐：首句简述 → 详细说明与使用语境 → 参数节（类型清楚）→ 返回节 → 错误节（失败模式与恢复指引）。

**原则 3：具体示例。** 典型调用、边界情况处理、错误响应与恢复动作。具体胜过泛泛：不写「用像 '123' 的 ID」，写「格式 'CUST-######'（如 'CUST-000001'）」；不写「提供一个日期」，写「格式 'YYYY-MM-DD'（如 '2024-01-15'）」。

## 命名规范

**参数名自解释。** 全词优先于缩写（id、url 这类公认缩写除外）；相同概念跨工具同名。好：customer_id、search_query、output_format、max_results、include_details。差：x、val、param1、info。

**枚举值一致。** 布尔类选项用前缀模式：include_（include_history、include_metadata）、exclude_（exclude_archived）。分类值术语统一：一律 format: "concise" | "detailed"，不要这边 short/long 那边 brief/complete。

## 错误信息设计

**双重读者。** 开发者要技术细节；Agent 要可执行指引。以 Agent 恢复为首要考虑：明确说哪里错、下一步做什么、输入错误附正确格式、附合法输入示例。

```json
{
  "error": {
    "code": "INVALID_CUSTOMER_ID",
    "category": "validation",
    "message": "客户 ID 'CUST-123' 不符合要求的格式",
    "expected_format": { "description": "客户 ID 必须 9 个字符", "pattern": "CUST-######", "example": "CUST-000001" },
    "resolution": "提供匹配 CUST-###### 的客户 ID",
    "retryable": true
  }
}
```

**常见错误模式。** 校验错误：收到了什么、期望什么、怎么改。限流：等多久、怎么重试。未找到：建议替代方式或核验步骤。系统错误：能否重试、有什么替代。

## 响应格式优化

**token 与准确性的权衡。** 冗长响应信息全但吃上下文；精简响应省 token 但可能缺细节。最优解是提供格式选项，让 Agent 按需选择。

**何时用哪种。** concise：快速核验或简单查找、只需确认、初次取回后的后续调用。detailed：基于数据做决策、输出成为其他处理的输入、正确性需要完整上下文。

## 工具集合设计

**管理工具膨胀。** 工具越多能力越多，但选择越难。描述重叠导致模型困惑。核心洞见：人类工程师说不清该用哪个的，Agent 也说不清。

**合并指引。** 把单一流程里的顺序步骤合并成一个处理整个流程的工具（如 schedule_event 替代 list_users + list_events + create_event）。行为根本不同的保持分开，哪怕功能有交集；不同语境使用的工具保持分离。相似领域的工具之间边界要清楚，尽量减少重叠。

**选择指引。** 多个工具都可能适用时，在描述里点明区别；用命名空间做逻辑分组。

## 测试工具设计

**评估标准。** 清晰性（Agent 能否判断何时用）、完整性（描述是否含全部必要信息）、可恢复性（Agent 能否从错误恢复）、效率（是否支持合适的响应格式）、一致性（是否遵循命名与 schema 规范）。

**Agent 测试模式。** 准备多样的 Agent 请求 → 让 Agent 为每个请求生成工具调用 → 对照期望模式评估正确性 → 归纳常见失败模式 → 据此精炼定义。

## 反模式

- **含糊描述**：「在数据库里搜索客户信息」→ 改为「按 ID 或邮箱取回客户信息。用户询问某客户详情、历史或状态时用。返回含 id、name、email、account_status 及可选订单历史的客户对象。」
- **神秘参数名**：x、val、param1。
- **缺错误处理**：通用错误或无错误处理。
- **命名不一致**：id / identifier / customer_id / user_id 混用。

## 上线前清单

描述清楚说明做什么、何时用；所有参数名字有意义、类型清楚；返回值有结构与示例；错误情况有可执行信息；遵循其他工具的命名规范；示例展示常见用法；响应大小差异大时提供格式选项。
