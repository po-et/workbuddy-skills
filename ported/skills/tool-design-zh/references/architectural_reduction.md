# 架构减法：生产证据

## 案例：文本转 SQL Agent

一个生产环境的文本转 SQL Agent 按架构减法原则重建。原架构：专用工具 + 重度提示词工程 + 精细的上下文管理。新架构：一个 bash 命令执行工具。

### 原架构（17 个专用工具）

GetEntityJoins、LoadCatalog、RecallContext、LoadEntityDetails、SearchCatalog、ClarifyIntent、SearchSchema、GenerateAnalysisPlan、FinalizeQueryPlan、FinalizeNoData、JoinPathFinder、SyntaxValidator、FinalizeBuild、ExecuteSQL、FormatResults、VisualizeData、ExplainResults。每个工具解决团队预想模型会遇到的一个问题：在复杂 schema 里迷路、写坏的 join、幻觉表名。

### 新架构（2 个原语工具）

ExecuteCommand（在沙箱里跑任意 bash）、ExecuteSQL（对数据库跑查询）。Agent 用 grep、cat、find、ls 在包含维度定义、指标计算、join 关系的 YAML / Markdown / JSON 文件里导航语义层。

### 对比结果

| 指标 | 原架构（17 工具） | 新架构（2 工具） | 变化 |
|---|---|---|---|
| 平均执行时间 | 274.8 秒 | 77.4 秒 | 快 3.5 倍 |
| 成功率 | 80%（4/5） | 100%（5/5） | +20% |
| 平均 token | 约 10.2 万 | 约 6.1 万 | 少 37% |
| 平均步数 | 约 12 | 约 7 | 少 42% |

原架构的最差用例：724 秒、100 步、145,463 token、失败。新架构同一查询：141 秒、19 步、67,483 token、成功。（数据来自该案例的公开分享，样本量小，视为方向性证据。）

## 为什么减法有效

**文件系统是强大的抽象。** 五十多年打磨；grep 这类标准工具文档完善、行为可预测、模型理解深。为 Unix 已解决的问题造自定义工具只增复杂度不增价值。

**工具在限制推理。** 专用工具解决的是模型本可以自己处理的问题：预过滤模型能导航的上下文、限制模型能评估的选项、用模型不需要的校验逻辑包装交互。每道护栏都成为维护负担；每次模型更新都要重新校准约束；团队花在维护脚手架上的时间超过了改进 Agent。

**好文档替代工具的精巧。** 语义层本就文档完善：结构化 YAML 的维度定义、命名清晰的指标计算、可导航的 join 关系。自定义工具只是在摘要本已可读的东西；模型需要的是直接读文档的权限，不是叠在上面的抽象。

## 实现模式

单个原语工具的描述示例：

```
在沙箱环境里执行一条 bash 命令。
用标准 Unix 工具探索并理解数据层：ls 列目录、cat 读文件、grep 搜模式、find 定位文件。
沙箱包含语义层文档：/data/entities/*.yaml 实体定义；/data/measures/*.yaml 指标计算；/data/joins/*.yaml join 关系；/docs/*.md 附加文档。
```

**成功前提：** 文档质量高（结构良好、命名一致、定义清楚）；模型能力足够；安全约束允许（沙箱限制访问与修改范围）；领域可通过文件检查导航。

**不适用：** 数据层混乱（遗留命名、无文档 join、结构不一致——模型只会更快地产出坏查询）；需要无法写进文件的专门知识；安全要求限制操作；流程确实复杂到受益于结构化编排。

## 设计原则

- **做减法。** 最好的 Agent 可能是工具最少的那个。每个工具都是替模型做的选择；给原语能力有时比给受限流程让模型做出更好的选择。
- **信任模型推理。** 因为不信任而限制推理往往适得其反。先测模型实际能做什么，再建护栏。
- **投资上下文，不是工具。** 清晰的文件命名、结构良好的文档、一致的数据组织、可读的关系定义。
- **为未来的模型而建。** 模型进步快于工具跟进。为今天的局限优化的架构对明天的能力可能过度约束。

## 评估框架

考虑架构减法时评估：维护开销（维护工具 vs 改进结果的时间比）；失败分析（失败源于模型局限还是工具约束）；文档质量（给模型直接访问，它能导航你的数据层吗）；约束必要性（护栏防的是真实风险还是假想担忧）；模型能力（工具设计以来模型进步了多少）。
