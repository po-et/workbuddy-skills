# 实测：SkillHub 的发布配额、slug 抢注与指标口径

写给准备在 SkillHub（skillhub.cn）上批量发技能的中文开发者。

这不是一篇成功学。这是一份实验记录：两天里我们往 SkillHub 发了 97 个技能，撞了四堵墙，做了几组对照实验去确认墙到底长什么样，最后发现自己引以为豪的"1084 次下载"其实说明不了什么。**每个结论后面都写了是怎么测出来的、样本多大、哪里可能错。凡是没测实的，一律标注"推测，需确认"。**

如果你只想看结论，跳到最后一节"给后来者的七条操作建议"。但我建议你看方法那几节——结论会随平台变化过期，方法不会。

---

## 一、我们做了什么

2026-09-16 到 09-17 两个晚上，我们把一个开源技能仓库里的内容分十二批发布到 SkillHub：

- 4 个原创技能打头阵（09-16 晚），验证流程跑得通；
- 然后是原创脚本工具（Dockerfile 体检、SQL 迁移风险、cron 解释、K8s 清单检查等约 22 个），以及一批宽松许可证作品的中文版；
- 09-17 晚上 18:23 到 23:14 之间集中发了 74 次（这是清单里有精确到秒的时间戳的记录数），把当晚的节奏拉到了极限；
- 09-18 又对 34 个技能补标签、补小节后升到 0.1.1 重发。

最后 `docs/submission-checklist.md` 里记了 97 个 slug。这批技能全部**不依赖任何 API Key**（平台有「不限 API Key」筛选项，需要 key 的会被过滤掉），带脚本的那些一律纯标准库、零第三方依赖。这点后面解释下载量时有用。

样本就这么大：**一个个人账号、97 个 slug、两天、一次全量指标快照**。所有数字都来自这个样本，不要当成平台的普遍规律。

## 二、撞到的四堵墙

### 墙 1：发布配额不是按日重置

这是最贵的一条经验，因为它直接决定你"今天还能发几个"。

**现象**：09-17 晚上把当天的发布量推到约 100 次成功之后，发布接口全面拦截，报"发布频率过高"。接着：

| 时间 | 动作 | 结果 |
|---|---|---|
| 09-17 23:00–23:14 | 34 个更新版重发 | 只成功 3 个（最后一次成功是 23:14:06） |
| 09-17 23:53 | 按 120 秒间隔重试 | 成功 0 个 |
| 09-18 00:54（约 +1 小时） | 再重试 | 成功 0 个 |
| 09-18 14:32（约 +14.5 小时） | 复验 | 仍然全部报"发布频率过高" |

注意 00:54 这个时间点：**本地日期已经翻篇**。14:32 这个时间点：**UTC 日期也已经翻篇**（对应 UTC 06:32）。两条"按日重置"的假设都被这两次复验直接否掉了。

**最符合的解释是：滚动 24 小时窗口，上限约 100 次。** 前一天的配额消耗集中在 18:00–23:53 这段，所以第二天要到同一时段才会逐步释放出来。

**这是推测，需确认。** 我们没有平台侧文档、没有返回头里的配额字段、也没有做"精确卡在第 N 次"的二分实验，只是在"不是按本地日、也不是按 UTC 日重置"这个确定的事实之上，选了最省事的解释。窗口到底是 24 小时还是别的长度、上限到底是 100 还是 90 或 120、是否按 slug/账号/IP 分桶计数——**全都没测过**。

### 墙 2：slug 抢注是真的，而且专挑热门英文名的 `-zh` 形式

我们复刻 superpowers 系列 10 个技能，其中 **8 个的 `-zh` slug 已经被别人占了**，只能改名：

| 原打算用的 slug | 实际发出去的 slug |
|---|---|
| `brainstorming-zh` | `brainstorming-spec-zh` |
| `writing-plans-zh` | `writing-impl-plans-zh` |
| `executing-plans-zh` | `executing-dev-plans-zh` |
| `verification-before-completion-zh` | `pre-completion-verification-zh` |
| `dispatching-parallel-agents-zh` | `parallel-agent-dispatch-zh` |
| `using-git-worktrees-zh` | `git-worktree-workflow-zh` |
| `receiving-code-review-zh` | `code-review-response-zh` |
| `finishing-a-development-branch-zh` | `dev-branch-finishing-zh` |

再往前，`triage-zh` 和 `context-compression-zh` 也各撞了一次，分别改成 `issue-triage-zh` 和 `context-compression-strategies-zh`。

**更要命的是一个反直觉的发现：slug 并不是全网强唯一的。** 我们有 3 个 slug（`code-review-zh`、`skillhub-publish-helper`、`pr-description`）和其他账号的技能**完全同名并存**，搜索结果里两边条目同时出现。也就是说：

- 发布时会因为 409 冲突被拒，但站内**确实存在**同名 slug 分属不同账号的情况（推测与早期渠道导入的历史数据有关，**需确认**）；
- 所以**光用 slug 关键词搜不足以定位到你自己的技能**，必须拿 `namespace.handle` 精确区分。我们踩过这个坑：账号页面上显示的 `user_a3a2e24a` 其实是接口返回的 `namespace.displayName`，真正的 `handle` 是 `indiv-captain`，两者指向同一个账号，但拿错了就匹配不上。

### 墙 3：文件格式与 frontmatter 的三条硬约束

三条都是被平台直接打回来才知道的，没有一条写在显眼的地方：

1. **无扩展名的文件会被拒收。** 目录里放了 `LICENSE`（或 `NOTICE`）就报 `400 不允许的文件类型: LICENSE`。许可证只能写进 frontmatter 的 `license` 字段。实测能通过的类型：`.md` / `.py` / `.yaml` / `.csv`。
2. **frontmatter 用的是严格 YAML 解析器。** 未加引号的值里出现半角冒号加空格（`: `）直接解析失败，报 `mapping values are not allowed in this context`。技能描述里写"用法: 如下"这种就会炸。解决办法只有一个：**整个值用双引号包住**，或者改用全角冒号。
3. **同 slug 重传必须升版本号。** 版本号不大于线上（或草稿）的最新版本就会被拒。批量改完再重发之前，先做一遍 `version` 自增。

这三条我们后来全部编码进了校验脚本，发布前先本地跑一遍，再没为这三件事浪费过配额——**这点很重要，因为失败的请求一样烧你的配额**。

### 墙 4：审核和 AI 评测是两条流水线，不要混为一谈

很多人会问"我的技能过审了吗"。在 SkillHub 上这句话其实指两件完全不同的事：

- **上架**：机器审核（内容合规、漏洞扫描、模型安全）通过后自动进搜索索引。**进了索引就算上架**，这是我们用的操作定义。
- **AI 评测报告**：技能详情页顶上那个"★★★★☆ 4.5（AI 评分）"，是另一条独立的、慢得多的批处理流水线。

09-17 20:55–21:00 我们对当时已发布的 82 个 slug 做了一次全量抽查：

| 口径 | 结果 |
|---|---|
| 搜索索引已可见（=上架） | **81 / 82（98.8%）** |
| 被拒绝 | **0** |
| AI 评测报告已生成 | **26 / 82（31.7%）** |

那唯一一个"未可见"的 `triage-zh`，复核后确认是**我们自己清单记录的问题**——它是撞名改发成 `issue-triage-zh` 的那一条，残留的记录没清掉。所以实际上 **82 个全部进了索引，一个都没被拒**。

而 AI 评测当时只覆盖了 31.7%，最早排队的已经等了近 3 小时。第二天（09-18 14:36）再查，覆盖率已经是 **95/95 = 100%**。结论：**评测是定时批处理，会追上，但它的进度和你的上架状态没有关系。** 看到评测 404 不要慌，那不是被拒。

## 三、我们是怎么验证的（方法比结论重要）

上面每一条都不是"我觉得"，下面写清楚怎么排除掉其他解释的。

### 3.1 用未改动的对照技能，排除"内容问题"

发布被拦的时候，第一反应通常是"是不是我这个包有问题"。我们的做法是：**在重试队列里放几个上一轮已经成功发布过、这次一个字都没改的技能**（只是升了补丁版本号）。如果内容有问题，它们上一轮就该失败；它们上一轮成功、这一轮和新技能一起失败，说明拦截和包内容无关。

结果：对照技能同样被拦。**"内容问题"这个解释被排除。**

这个设计很便宜，但很多人不做，直接就去改包了——然后一边改一边烧配额，越改越乱。

### 3.2 用读操作，排除"令牌失效"

第二个常见怀疑是"token 过期了"。我们在同一时间段用同一套凭据跑只读接口：`skillhub search`（搜索）和 `skillhub skill evaluation`（评测查询），**全部正常返回**。

结论：账号和凭据是好的，被限的只有写路径。**"令牌失效"这个解释被排除。**

顺带一提，这组只读查询本身也是一次压力测试：82 个 slug × 2 次调用、固定 1.3 秒间隔、总耗时 300.9 秒，**全程没触发任何限流**。这进一步说明读写是两套配额。

### 3.3 用跨日复验，排除"按日重置"

这是唯一能证伪"每天 100 次"这种直觉假设的办法：**在本地日期翻篇之后试一次（00:54），在 UTC 日期也翻篇之后再试一次（14:32）**。两次都还在被拦，"按日重置"就站不住了。

这里必须承认一个方法缺陷：我们**没有做连续采样**。真正干净的实验应该是从被拦那一刻起，每 30 分钟探一次（用同一个对照技能），记录第一次放行的时刻，用"第一次放行时刻 - 首次消耗时刻"去反推窗口长度。我们只探了 3 个点（+1h、+14.5h 加上中间的重试），**所以"滚动 24 小时"只能是推测，不能当结论**。

### 3.4 单次发布间隔是怎么定到 75 秒的

早期实测：连续 3 次请求（**含失败的**）之后，第 4 次就报"发布频率过高"。于是脚本固定 75 秒间隔串行发布，在配额充裕时基本不会撞。

但要注意：**接近配额上限时，75 秒不够**，会偶发限流。这时候正确的动作是**对同一个技能等 10 分钟级别再重试，而不是跳过它去发下一个**——跳过只会让你更快耗尽剩余额度，而且把队列搞乱。

### 3.5 指标是怎么拿到的

官方 CLI 的 `search` / `skill reports` 子命令**不显示** downloads/installs/stars 这些字段。但读 CLI 源码（`~/.skillhub/skills_store_cli.py`）可以确认一件事：**这些字段本来就在 CLI 已经拿到的响应体里，只是打印前被过滤掉了**。

- `skillhub search --json` → 调 `GET /api/v1/search`，客户端函数把 `downloads/installs/stars` 过滤掉，只留 slug/name/description 等；
- `skillhub skill reports <slug> --json` → 调 `GET /api/v1/skills/{slug}`，拿到了完整响应体，但只打印 `securityReports` 一段；
- `skillhub skill evaluation <slug> --json` → 调 `GET /api/v1/skills/{slug}/evaluation`，这个是唯一把响应体整体透出的。

所以我们直接调同一个详情接口取 `skill.stats`。**这里没有绕过任何鉴权**：读 CLI 的请求头构造函数可以确认，它对这三个接口本来就**不带 Authorization**，只带 UA 和一个匿名 client-id；我们原样复现，不多加不少加。

**局限要说清楚**：这三个接口不是官方公开 API 文档里正式列出的（据目前所知不存在这样一份文档），是从已安装 CLI 版本的实现细节里读出来的。平台没有对字段和稳定性做任何承诺，随时可能变。如果哪天脚本大面积报错，第一怀疑对象是接口变了。

## 四、指标：能拿到什么，拿不到什么

**能拿到**（`GET /api/v1/skills/{slug}` 的 `stats` 字段，2026-09-18 实测确认）：

| 字段 | 含义 |
|---|---|
| `downloads` | 下载量 |
| `installs` | 安装量（走 `skillhub install` 本地安装路径的次数） |
| `stars` | 收藏数（**注意是收藏，不是 1–5 星评分**） |
| `comments` | 评论数 |
| `versions` | 已发布版本数 |

加上详情接口里的展示名、分类、创建/更新时间、最新版本号、安全扫描状态，以及 `/evaluation` 接口的 AI 评测分（5 个维度 × 每维度若干子项，各 1–5 分）。

**确认拿不到**：

- **查看量 / 浏览量（views / PV）**。CLI 全部子命令、三个原始接口、网页技能详情页（实测打开自己的技能页，只显示"N 次下载 / N 次收藏 / tokens 预估消耗"），**都没有这个字段**。这不是权限不够或方法不对，是平台当前不向开发者暴露。如果要，只能去问平台方（**后台有没有、只是不对外，我们无法排除，需确认**）。
- **用户打分**。不存在"用户给技能打星"。唯一的"评分"是 AI 评测分，评的是文档和脚本质量，不是用户满意度。

顺带一个观察：网页上显示的那个星级，实测就是**全部子项打平取算术平均**（拿一个技能核对过：15 个子项平均 4.5，页面显示也是 4.5）。如果你自己算，先按维度求均值再对维度求均值，会和页面差 0.0x。

## 五、下载量的解读陷阱：为什么 1084 次说明不了什么

2026-09-18 我们跑了第一份全量快照，97 个 slug 里 95 个查得到详情（另外 2 个：一个是清单记录残留，一个被边缘安全策略拦了，返回 HTTP 566，用官方 CLI 能复现同样的错误）。

| 指标 | 数值 |
|---|---|
| 下载量合计 | **1084** |
| 均值 / 中位数 | 11.4 / **11** |
| 最高 / 最低 | 48 / 0 |
| 安装量、收藏、评论合计 | **全部为 0** |
| 已进搜索索引 | 95/95 = 100% |

看起来还行？我们自己算了两个数之后就不这么想了。

**第一，分布过于集中。** 95 个技能里 **88 个（92.6%）的下载量挤在 6–20 这个区间**。0 次的 2 个、1–5 次的 2 个、21 次以上的只有 3 个。如果下载真的由"技能有多好用、多对路"驱动，一个涵盖 Dockerfile 体检、周报生成、上下文工程、前端 UI 的异质集合，不可能挤成这样。

**第二，唯一和下载量有关的变量是"上架多久"。** 我们算了上架时长（首次创建时间到查询时刻的小时数，范围 15.9–44.0 小时）与下载量的相关系数：

- Pearson **r = 0.41**（r² = 0.17）
- Spearman **ρ = 0.59**

同时，AI 评测分（4.34–4.73）与下载量的相关系数是 **r = −0.13**，也就是**基本无关**。

**判断：当前这 1084 次累计下载，主要由"上架时长"和"平台基线抓取"驱动，不足以证明真实用户需求差异。** 换句话说，一个技能挂上去，不管它是什么，过一天大概都会积攒 10 次左右的下载。

这个判断也有它的边界：上架时长只解释了 17% 的方差（Pearson）；"平台基线抓取"这个说法本身是**推测，需确认**——我们没有任何日志能证明这些下载来自爬虫、镜像或平台内部预取，只是从"分布过于集中 + 与内容特征无关 + 互动指标全 0"反推出的最简解释。也不能排除是真实用户的随机浏览行为叠加。

但有一件事是确定的：**安装、收藏、评论三项全平台为 0**。没有人收藏，没有人评论，没有人走本地安装路径。这三个数字和下载量来自同一个响应体，不是我们漏抓了字段。真实的用户互动，目前是零。

**所以：不要看累计值，要看每日增量。** 累计下载量里混着一个随时间线性增长的基线，你从中读不出任何关于"哪个技能更受欢迎"的信息。每天固定时间抓一次快照，看**同一个技能的日增**、看**不同技能日增的差异**，那才是信号。我们目前只有 09-18 这一个时间点，**连第二个点都还没有，所以严格来说增长分析还没开始**。

## 六、给后来者的七条操作建议

1. **把发布配额当稀缺资源做预算。** 动手前先算：我总共要发 N 个，最近 24 小时已经发了 M 次。按上限约 100（**推测值，需确认**）规划，**单日不超过 90 次**留 10 次给重试和失败。
2. **不要在几小时内打满。** 一晚上 100 次打满的代价是第二天同一时段之前你什么都发不了。把批次摊到一天里的几个时段，滚动窗口才会持续给你放行额度。
3. **发布前本地全量校验。** 失败的请求一样烧配额。无扩展名文件、frontmatter 里未加引号的 `: `、版本号没升——这三样在本地跑一遍脚本就能全查出来，别拿线上配额当 linter。
4. **slug 命名带限定词。** 热门英文名的 `-zh` 形式是重灾区，`brainstorming-zh`、`writing-plans-zh` 这类基本没了。加一个说明用途的词（`brainstorming-spec-zh`、`writing-impl-plans-zh`）既能避开冲突，**又能提高搜索时的语义精度**——这不是退而求其次。
5. **发布节奏：正常 75 秒间隔，接近配额时切 10 分钟退避。** 遇限流对**同一项**重试，不要跳过去发下一个。
6. **区分"上架"和"评测"。** 进搜索索引就是上架了，可以去宣传了；AI 评测 404 只是还在批处理队列里，不是被拒。用搜索接口按 `slug + namespace.handle` 精确判断可见性，不要只搜 slug 关键词（会搜到别人的同名技能）。
7. **指标只看日增，别看累计。** 第一天就把快照脚本接上定时任务，原始 CSV 一份都别删。真正有价值的数字是第二份快照减第一份。

## 七、哪些还没搞清楚

诚实地列出来，这些都是我们**没有**证据的：

- **配额窗口的真实长度和上限。** "滚动 24 小时、约 100 次"是最省事的解释，不是结论。需要连续采样（每 30 分钟用同一个对照技能探一次，记录第一次放行时刻）才能确认。
- **配额是怎么分桶的。** 按账号？按 IP？按 slug？失败的请求是否和成功的一样计数（早期"连续 3 次含失败"的观察暗示会，但没有做隔离实验）？全都没测。
- **下载量到底来自哪里。** 没有任何来源维度的数据，"平台基线抓取"是推测。
- **AI 评测批处理的周期。** 只知道从 31.7% 到 100% 用了不到一天，具体多久跑一轮、触发条件是什么，不知道。
- **AI 评测分是否影响搜索排序和曝光。** 我们的样本里评测分和下载量相关系数是 −0.13，**但这个样本的分数区间太窄（4.34–4.73），根本测不出区分度**。不能据此说评分没用。
- **slug 同名并存的成因。** 推测和早期渠道导入的历史数据有关，需确认。
- **`dockerfile-check` 的 HTTP 566。** 详情接口被腾讯云 EdgeOne 的 WAF 拦了，官方 CLI 能复现，原因不明。
- **上架时长与下载量的关系是不是线性的。** 我们的样本上架时长只覆盖 15.9–44.0 小时，跨度不到两天，外推到一周以上没有依据。
