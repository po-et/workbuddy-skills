# 上线前五分钟：用 WorkBuddy 把 Dockerfile / K8s / SQL / OpenAPI / .env 五项检查串成一条 CI 门禁

**所处行业与岗位**：互联网软件研发，后端 / 全栈工程师，兼任小组的发布负责人。

**用 WorkBuddy 完成的工作**：发版前对着一个服务做一次「上线前五分钟体检」——镜像里有没有把密钥打进去、K8s 清单有没有资源限制和探针、这次的迁移 SQL 会不会锁表丢数据、接口定义有没有悄悄改坏、生产环境是不是少配了一个变量——一条命令跑完，出一份带「能不能上线」结论的报告；确认可用之后，把同一条命令接进 CI，让它以后自动拦。

以前这件事靠一张人工 checklist，四五个人在发布群里对着念，念到第三条就开始跳着念。现在是一条命令 0.2 秒，加上我按报告逐条改，一轮 20 分钟。

## 一、背景：上线前那五分钟，我们到底在慌什么

复盘过去几次线上问题，事后看**全都能在提交代码之前静态看出来**：

- 镜像 `ENV` 里留了一行数据库密码，镜像层永久保留，换密码也删不掉历史层；
- Deployment 没配 `resources`，一次流量高峰把节点内存吃满，邻居服务一起挂；
- 迁移脚本里一条 `ALTER TABLE ... ADD COLUMN ... NOT NULL`（没有 DEFAULT），在有数据的表上直接失败，发布卡在一半；
- 接口把响应字段 `total_fee` 改名成 `amount`，自己的前端跟着改了，但两个下游调用方不知道；
- `.env.production` 少了一个 `ORDER_CALLBACK_URL`，服务起来了，回调静默丢弃。

这五类问题的共同点是：**都能靠读文件查出来，不需要连集群、不需要连数据库、不需要真的构建**。但它们分属五个工具、五个人的习惯，没有人会在发版前依次跑五遍。所以真实世界里的结局往往是：都不跑。

我要的不是一个更全的工具，而是**一条命令、一个结论、一个能塞进 CI 的退出码**。

## 二、方案设计：一条命令、五项检查、一个门禁结论

WorkBuddy 这边我没有装大而全的东西，用的是六个开源、纯 Python 标准库的 Skill：一个总入口 + 五个单项检查器。

| 检查项 | 看什么 | 典型 high | 单项技能 |
|---|---|---|---|
| Dockerfile | 17 条最佳实践与安全规则：基础镜像未固定、root 运行、缓存层失效、管道执行远程脚本 | `ENV`/`ARG` 把密钥写进镜像层 | `dockerfile-check` |
| K8s 清单 | 17 条生产就绪基线：资源 requests/limits、探针、安全上下文、镜像标签、selector 匹配 | 环境变量里明文写密码 | `k8s-manifest-check` |
| SQL 迁移 | 16 条锁表与不可逆风险规则，自动识别 MySQL / PostgreSQL 方言 | DROP COLUMN、没有 WHERE 的 UPDATE/DELETE | `sql-migration-check` |
| OpenAPI 兼容 | 新旧两份规范的破坏性变更：接口删除、参数变必填、响应字段消失或改类型 | 删接口、响应字段不再保证返回 | `openapi-breaking-diff` |
| .env 配置 | 示例文件、环境文件、代码三方对齐，以及疑似真实密钥 | 环境文件缺了示例中登记的变量 | `env-sync-check` |

总入口 `release-readiness-check` 做四件事：**发现 → 执行 → 汇总 → 判门禁**。它走一遍目标目录（跳过 `.git`、`node_modules`、`vendor`、`dist` 这类目录），按特征归类文件：`Dockerfile*`、同时含 `apiVersion:` 与 `kind:` 的 YAML、`*.sql`、`openapi*/swagger*` 规范、根目录的 `.env*`；然后逐项用子进程调用内置的五个检查器（统一加 `--json`），把五种不同结构的结果归一成 `severity / code / where / message / fix`，最后按门禁规则给结论：**有 high 就是「不建议上线」；没有 high 但有项目拿不到证据（子脚本跑失败、规范不合格）同样不放行**——三态门禁，不是有没有 high 这一种两态判断，「无法判断」不等于「通过」（细节见第五节「复盘与边界」）。

几个刻意的设计选择，是这套东西能真跑起来的原因：

- **零依赖、不联网**：纯 Python 标准库，不执行构建、不 apply 清单、不连数据库、不调线上接口，只读文件。所以它可以放在任何一台构建机上，也不需要申请任何权限。
- **单项失败不拖累整体**：某个检查器挂了（脚本缺失、超时 180 秒、输出不是合法 JSON），或者证据本身不合格（比如 OpenAPI 拿不到旧版本规范），只标「无法判断」，另外四项照跑；报告里会写明「无法判断」是没拿到证据、不是「通过」，`--strict` 下这一项也会让退出码变成 1。
- **每条 finding 都带「→ 改法」**：报告不是骂人清单，是可执行的 diff 提示。这一点决定了 WorkBuddy 能不能接着帮你改。
- **WorkBuddy 的分工**：确定性的部分（扫文件、匹规则、算数量、排序、出报告）全在脚本里，模型负责读报告、判断哪几条在这个项目里是真问题、给出具体改法、改完复跑。这和「把 Dockerfile 贴给 AI 让它看看」的区别是：规则命中零幻觉，判断部分可核对。

配置上不需要专家、连接器或 MCP，默认权限（只读本地目录 + 执行 python3）即可。

### 演示项目：一个故意写坏的 orders-api

为了让下面每一行输出都能复现，我按真实项目里最常见的写法造了一个最小服务 `orders-api`（域名统一用 `example.com`），11 个文件：

```text
orders-api/
├── Dockerfile
├── requirements.txt
├── .env.example
├── .env.production
├── app/
│   ├── config.py          # 读 DB_DSN / REDIS_URL / ORDER_CALLBACK_URL / FEATURE_NEW_PRICING / PAYMENT_TIMEOUT_MS
│   └── main.py
├── k8s/
│   ├── deployment.yaml
│   └── service.yaml
├── migrations/
│   └── 0042_add_channel.sql
└── api/
    ├── openapi.json       # 本次要发的 1.5.0
    └── openapi.v1.json    # 上一版 1.4.0，用于比对
```

几个关键文件长这样（错误是故意的，都是我在真实仓库里见过的写法）：

```dockerfile
FROM python:3.11
WORKDIR /app

RUN apt-get update
RUN apt-get install -y curl libpq-dev

COPY . .
RUN pip install -r requirements.txt

ENV DB_PASSWORD=orders_pg_2026
ENV APP_ENV=production

EXPOSE 8080
CMD python -m app.main
```

```sql
-- migrations/0042_add_channel.sql
ALTER TABLE orders ADD COLUMN channel VARCHAR(32) NOT NULL;

UPDATE orders SET channel = 'web';

ALTER TABLE orders DROP COLUMN source_legacy;

CREATE INDEX idx_orders_channel ON orders (channel);
```

`k8s/deployment.yaml` 里 `image` 是 `registry.example.com/orders-api:latest`，没有 `resources`、没有探针，`env` 里一行 `DB_PASSWORD: orders_pg_2026` 明文；`.env.production` 比 `.env.example` 少一个 `ORDER_CALLBACK_URL`；接口这一版把 `total_fee` 改名成 `amount`、删掉了 `DELETE /orders/{id}`、把 `page_size` 改成必填。

### 第 2 步：第一次体检的真实输出

终端回显（真实，2026-09-18 本机实跑）：

```text

  K8s 清单体检            high 1 / warn 5 / info 8
  SQL 迁移风险            high 3 / warn 0 / info 1
  OpenAPI 破坏性变更      high 8 / warn 0 / info 5
  .env 一致性             high 2 / warn 2 / info 1

合计：high 15 / warn 9 / info 22；无法判断 0 项

```

**15 个 high。** 三次连续运行的墙上时间分别是 0.19s / 0.16s / 0.15s——「五分钟体检」里那五分钟是给人读报告用的，脚本本身不到一秒。

报告固定三段（总览 / 各项问题 / 门禁结论），15 个 high 逐条摘录：

```markdown
### Dockerfile 体检
- **[HIGH]** `DF006` · `Dockerfile:L10` — ENV 中疑似把敏感值写进镜像：DB_PASSWORD
  - → 改法：镜像层会永久保留该值；改用运行时注入（-e / secrets）或 BuildKit 的 --mount=type=secret

### K8s 清单体检
- **[HIGH]** `K010` · `k8s/deployment.yaml Deployment/orders-api` — 容器 orders-api 的环境变量 DB_PASSWORD 以明文 value 写入清单
  - → 改法：改用 valueFrom.secretKeyRef 引用 Secret

### SQL 迁移风险
- **[HIGH]** `SM003` · `migrations/0042_add_channel.sql:L2` — 新增列 channel 为 NOT NULL 但没有 DEFAULT
  （语句 `ALTER TABLE orders ADD COLUMN channel VARCHAR(32) NOT NULL`）
  - → 改法：已有数据行会导致失败或需要全表回填；先加可空列 → 回填 → 再设 NOT NULL，或提供 DEFAULT
- **[HIGH]** `SM006` · `migrations/0042_add_channel.sql:L4` — UPDATE/DELETE 没有 WHERE
  （语句 `UPDATE orders SET channel = 'web'`）
  - → 改法：补上 WHERE；大表分批（LIMIT / 主键区间）执行
- **[HIGH]** `SM001` · `migrations/0042_add_channel.sql:L6` — DROP COLUMN 会永久删除该列数据
  （语句 `ALTER TABLE orders DROP COLUMN source_legacy`）
  - → 改法：采用扩展-收缩：先让代码不再读写该列并发布，再在后续迁移里删除

### OpenAPI 破坏性变更
- **[HIGH]** `removed-operation` · `DELETE /orders/{id}` — 接口被删除
- **[HIGH]** `param-now-required` · `GET /orders` — 参数 query:page_size 由可选变为必填
- **[HIGH]** `response-enum-narrowed` · `GET /orders` — 响应 200 字段 items.[].status 枚举移除了 ['cancelled']（客户端可能依赖这些取值）
- **[HIGH]** `response-field-no-longer-required` · `GET /orders` — 响应 200 字段 items.[].total_fee 不再保证返回
- **[HIGH]** `response-field-removed` · `GET /orders` — 响应 200 字段 items.[].total_fee 被移除
- **[HIGH]** `response-enum-narrowed` · `GET /orders/{id}` — 响应 200 字段 status 枚举移除了 ['cancelled']（客户端可能依赖这些取值）
- **[HIGH]** `response-field-no-longer-required` · `GET /orders/{id}` — 响应 200 字段 total_fee 不再保证返回
- **[HIGH]** `response-field-removed` · `GET /orders/{id}` — 响应 200 字段 total_fee 被移除

### .env 一致性
- **[HIGH]** `secret-in-example` · `.env.example` — 示例文件第 10 行的 JWT_SIGNING_KEY 看起来是真实密钥，示例文件会被提交到仓库
- **[HIGH]** `missing` · `.env.production` — .env.production 缺少示例中登记的 ORDER_CALLBACK_URL
```

报告里每项最多列 10 条（已按严重度排序），超出会提示去跑单项技能看全量。K8s 这项实际 14 条，于是单跑一次：

### 第 3 步：按「→ 改法」逐条改

这一步是 WorkBuddy 干活最爽的地方：报告里每条都带改法，它按项给出 diff，我只负责判断「这条在我们项目里算不算真问题」。

- **`DF006`**：删掉 `ENV DB_PASSWORD=...`，密码改运行时注入。
- **`K010`**：`value: orders_pg_2026` 换成 `valueFrom.secretKeyRef`（`name: orders-api-db`，`key: password`）。
- **`SM001/SM003/SM006`**：把一次性迁移拆成扩展-收缩两阶段——本次只加可空列 + 带 WHERE 的分批回填 + `CREATE INDEX CONCURRENTLY`，`SET NOT NULL` 和 `DROP COLUMN source_legacy` 留到「代码不再读写该列、上线一周后」的 0044：

```sql
-- 0042 订单来源渠道（扩展阶段：只加可空列 + 分批回填，不删旧列）
ALTER TABLE orders ADD COLUMN channel VARCHAR(32);

UPDATE orders SET channel = 'web' WHERE channel IS NULL AND id <= 100000;

CREATE INDEX CONCURRENTLY idx_orders_channel ON orders (channel);

-- 收缩阶段（0044，等代码不再读写 source_legacy 且上线一周后再执行）：
--   ALTER TABLE orders ALTER COLUMN channel SET NOT NULL;
--   ALTER TABLE orders DROP COLUMN source_legacy;
```

- **OpenAPI 八条**：不改 API 设计，改兼容方式——`DELETE /orders/{id}` 加回来，`page_size` 恢复可选，`total_fee` 与新字段 `amount` **同时保留且同时必返**，`total_fee` 标 `deprecated` 并在 description 里写「use amount」，被收窄的 `status` 枚举值 `cancelled` 加回去。版本号 1.5.0 → 1.5.1。八条里有两条是 `response-enum-narrowed`（`GET /orders` 和 `GET /orders/{id}` 各一条）——同一个 `status` 枚举收窄，因为两个接口共用 `Order` 这个 schema，所以两处各报一次；改法是同一个：把 `cancelled` 加回枚举。
- **`.env` 两条**：`.env.production` 补 `ORDER_CALLBACK_URL`；`.env.example` 里的 `JWT_SIGNING_KEY` 换成 `<jwt-signing-key>` 这种一眼是占位符的写法（`DB_DSN` 这次没有被判成密钥，原因见第五节边界 1）。顺手把 `undocumented` 那条 warn 也修了——代码里读的 `PAYMENT_TIMEOUT_MS` 登记进 `.env.example`。

### 第 4 步：复跑，以及「修 warn 修出一个新 high」

复跑之后 high 从 15 掉到 **1**——而且这个 1 是我刚刚自己造出来的：

```text
  .env 一致性             high 1 / warn 1 / info 1
```

```markdown
- **[HIGH]** `missing` · `.env.production` — .env.production 缺少示例中登记的 PAYMENT_TIMEOUT_MS
```

原因是这个检查器的语义很硬：**示例文件里登记的变量，每个环境文件都必须有**。我为了消掉「代码读了但示例没登记」这条 warn，把 `PAYMENT_TIMEOUT_MS` 写进了 `.env.example`，于是 `.env.production` 立刻变成「缺变量」。

这不是 bug，是设计取向：它不认「代码里有默认值所以可以不配」这种隐式约定。真实项目里我也认同这个取向——一个上线后靠代码默认值兜底的超时参数，正是最容易在某个环境上被忘掉的东西。所以正确的收敛方式是把它显式写进 `.env.production`，而不是从示例里删掉。补上之后：

```text
上线体检 · /.../demo/orders-api-fixed
  Dockerfile 体检         high 0 / warn 2 / info 7
  K8s 清单体检            high 0 / warn 5 / info 8
  SQL 迁移风险            high 0 / warn 0 / info 0
  OpenAPI 破坏性变更      high 0 / warn 0 / info 5
  .env 一致性             high 0 / warn 1 / info 1

合计：high 0 / warn 8 / info 21；无法判断 0 项
门禁：可以上线，但先看一眼 warn
```

SQL 那项从 `high 3 / info 1` 变成全 0；OpenAPI 剩下的 5 条 info 是纯新增（新增可选参数 `channel`、响应新增 `amount` 与 `channel`），正好可以直接抄进变更日志发给调用方。剩下 8 个 warn 是镜像 latest、缺 requests/limits、缺 readinessProbe、未声明 runAsNonRoot、`.env.production` 里的真密钥这类——**它们该修，但不该阻塞这次发布**，这正是 warn 这一级存在的意义。

### 第 5 步：接进 CI 当门禁

到这里体检是「人跑一次」，价值只覆盖这一次发布。接进 CI 才是长期收益。`--strict` 在有 high 时退出码 1：

```bash
$ python3 scripts/release_check.py . --openapi-base api/openapi.v1.json --strict --out release-report.md
...
门禁：不建议上线
$ echo $?
1
```

修完之后同一条命令退出码 0。GitHub Actions 里的完整写法（在 bash 下实跑验证过两个分支）：

```yaml
name: release-gate
on: [pull_request]

jobs:
  readiness:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - name: 上线体检
        run: |
          # 技能目录 vendor 进仓库里（路径按你自己的放法改，也可以在这一步 git clone 技能仓库）
          SCRIPT=vendor/release-readiness-check/scripts/release_check.py
          BASE_REF="${GITHUB_BASE_REF:-main}"
          if git show "origin/$BASE_REF:api/openapi.json" > /tmp/openapi-base.json 2>/dev/null; then
            python3 "$SCRIPT" . --openapi-base /tmp/openapi-base.json --out release-report.md --strict
          else
            echo "[warn] 取不到 origin/$BASE_REF 的 api/openapi.json，本次跳过 OpenAPI 比对"
            python3 "$SCRIPT" . --skip openapi --out release-report.md --strict
          fi
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: release-report
          path: release-report.md
```

GitLab CI 同理，把 `script` 换成同样三行，`artifacts:paths` 收 `release-report.md`。

这里有个**踩过的坑，顺带说一下它现在的状态**：本文最初写这一节时，我图省事把「取不到旧规范」的兜底写成 `|| echo '{}' > /tmp/openapi-base.json`。当时实测的结果是——空规范当 base，所有接口都被算成「新增」，OpenAPI 这项返回 `high 0 / warn 0 / info 3`，**给出一个漂亮的假绿灯**：哪怕这次发布删了接口、改了必填参数，门禁也会显示「可以上线」。

这个缺陷后来被修掉了，写这篇文章的过程里我又用同样的空文件复测了一次（2026-09-18 本机实跑，`orders-api` 仍是文中那个「破坏性改动」版本）：

```bash
$ echo '{}' > /tmp/openapi-base.json
$ python3 scripts/release_check.py . --openapi-base /tmp/openapi-base.json --strict --out release-report.md
上线体检 · /.../orders-api
  Dockerfile 体检         high 1 / warn 2 / info 7
  K8s 清单体检            high 1 / warn 5 / info 8
  SQL 迁移风险            high 3 / warn 0 / info 1
  OpenAPI 破坏性变更      无法判断（skipped-invalid）：规范不合格，无法比对（拿不到证据，不计入通过）：
                        `/tmp/openapi-base.json` 缺少 openapi / swagger 版本字段，不像一份 OpenAPI 规范
  .env 一致性             high 2 / warn 2 / info 1

合计：high 7 / warn 9 / info 17；无法判断 1 项
门禁：不建议上线
$ echo $?
1
```

不再是假绿灯，而是「无法判断」——release-readiness-check 现在会先校验两份规范本身合不合格（有没有 `openapi`/`swagger` 版本号、`paths` 里有没有接口），不合格就直接把 OpenAPI 这一项标记为「无法判断」，不会当成「没有变更」悄悄放过。这也是现在整个工具的门禁设计：**三态，不是「有 high / 没 high」两态**。有 high → 不建议上线；没有 high 但有项目「无法判断」（子脚本跑失败、规范不合格、拿不到旧版本）→ 同样不放行，`--strict` 退出码照样是 1；只有全部项目都有结论、且没有 high → 才放行。「拿不到证据」不再等于「通过」，这条边界现在是代码保证的，不用靠 CI 脚本自己把兜底写对。

不过我在 CI 里还是建议显式写 `--skip openapi`（报告里会明写「跳过：按 --skip 跳过」，语义比「凑巧被判成无法判断」更清楚，也不依赖 `git show` 恰好失败），下面的 workflow 保留这个写法。

另外三个参数在 CI 里也用得上：`--json` 输出 `{target, generated, report, total, gate, items[]}`（`gate` 是门禁结论本身：`verdict/blocked/headline/why` 加上未通过项列表；`items[]` 每项含 `status / reason / targets / counts / findings`），可以直接喂给机器人发到群里；`--skip dockerfile,k8s` 用于分仓库拆流水线；`--out` 指定报告路径，不给就写系统临时目录并打印绝对路径。

## 四、产出物与效果

**产出物**：一份 Markdown 报告（总览表 → 各项 top 问题 → 门禁结论），一个退出码，可选一份 JSON。报告能直接贴进上线单，因为它满足发布评审真正要的三件事——**每条有位置（文件:行号 / 对象名 / 方法+路径）、有规则号、有改法**。

**这一轮的真实数字**：

| | 第一次 | 修完 high | 终态 |
|---|---:|---:|---:|
| high | 15 | 1 | **0** |
| warn | 9 | 1（.env 项） | 8 |
| info | 22 | — | 21 |
| 门禁结论 | 不建议上线 | 不建议上线 | 可以上线，但先看一眼 warn |
| `--strict` 退出码 | 1 | 1 | 0 |

**验收标准**（我发出去之前按这个检查）：

1. high 清零，且每条清零都是真改了配置，不是加白名单。
2. 报告里「跳过 / 无法判断」的项都有说明，没有静默放过——特别是 OpenAPI 项，拿不到旧规范或旧规范不合格，都必须显示「无法判断」而不是当成没有变更。
3. 剩下的 warn 逐条有人认领：这次发布不改的，写进下个迭代的技术债条目。

**值得记的效果**：15 个 high 里，靠人工 checklist 能稳定抓住的大概只有 Dockerfile 那条明文密码（因为它最出名）。`SM003`（NOT NULL 无 DEFAULT）、`param-now-required`、`missing`（生产少一个变量）这三类，是那种「上线当晚才发现」的典型，而它们在提交代码之前就能查出来。

## 五、复盘与边界

这套东西的价值上限，取决于你有多清楚它查不到什么。四条边界都是实跑撞出来的：

**1. 误报是真的存在——但这次实跑抓到的例子换了一个，值得如实记一下这个变化。** 最初写这篇文章时，`.env.example` 里那行 `DB_DSN=postgresql://user:pass@localhost:5432/orders` 被判成 `secret-in-example`（high）：它其实是个占位符，判它是密钥属于误报。这条误报后来被 env-sync-check 自己的修复消掉了——密钥判断改成「名字 + 值」双重条件，连接串类的值现在只截取内嵌的密码段来判断（这里是 `pass`，4 个字符），长度不够 12 就不算「像密钥」，所以这次实跑 `DB_DSN` 完全没有被提示，无论是 `.env.example` 还是 `.env.production`。

但双重判定没有让误报消失，只是换了个地方冒出来：这次实跑里，`.env.production` 第 4 行的 `JWT_SIGNING_KEY=REPLACED_BY_SECRET_MANAGER` 被判成 `secret`（warn）。`SIGNING` 命中了密钥类命名规则，而 `REPLACED_BY_SECRET_MANAGER` 长度够、大小写与下划线混杂，占位符词表里又没收录「REPLACED_BY_...」这种「真值由密钥管理系统接管」的团队写法，于是被当成了真密钥。它其实不是密钥，是一句人话注释。**不要为了清零去改坏配置**——这条结论没变；只是提醒一句：改法要么把值换成词表认识的占位形态（`<...>`、`changeme` 这类），要么在评审里记录下来接受它，具体命中哪个变量会随规则版本变化，不能死记硬背某一个变量名。

**2. 漏报也是真的存在——但这次的两个例子，此前发现的漏报点都已经被修掉了，这也是本文改动最大的地方。** 最初写这篇文章时有两处漏报：`.env.example` 里 `JWT_SIGNING_KEY=8f14e45fceea167a5a36dedd4bea2543`（一串 32 位十六进制，长得非常像真密钥）没有被判成密钥——当时的名字规则只认 `API_KEY / PRIVATE_KEY / ACCESS_KEY` 这几种带前缀的写法，`JWT_SIGNING_KEY` 不在名单里；OpenAPI 那边，这一版把响应字段 `status` 的枚举值 `cancelled` 删掉了，属于典型的响应枚举收窄，当时的规则只覆盖「参数」和「请求字段」的枚举收窄，不覆盖响应字段，所以也没报。

这两处后来都被修了：env-sync-check 的密钥名字规则加了 `SIGNING`/`JWT` 这类前缀，这次实跑 `JWT_SIGNING_KEY` 在 `.env.example` 里被判成 `secret-in-example`（high，见前面「15 个 high 逐条摘录」）；openapi-breaking-diff 新增了 `response-enum-narrowed` 规则，这次实跑 `status` 枚举收窄在 `GET /orders` 和 `GET /orders/{id}` 各报了一条 high——这正是本文把 OpenAPI 的 6 个 high 更正成 8 个的原因。**结论要分两半看**：「报告干净 ≠ 没问题」这条判断依然成立，它只是提醒你「当前这版规则没覆盖到」，覆盖范围本身会随版本变化，不是跑一次就能一劳永逸；密钥扫描仍然建议另配专门工具兜底，接口语义变化仍然要靠评审，不能只靠这一层规则兜底。

**3. 它不替代专业工具，只是把门禁提前。** hadolint、kubeconform、OPA/Conftest、DBA 评审各自的规则集都更全，也更准。这套技能的定位是**提交代码之前的第一道快速门禁**：零依赖、0.2 秒、五类一起、有退出码。真正的最后一道关卡还是评审和专业工具。

**4. 几个硬限制要提前知道**，否则会出现「跑了但其实没查」：OpenAPI 项**必须给 `--openapi-base`**，只有一份规范、或者给的规范不合格时都会标为「无法判断」，不会被当成没有变更悄悄放行；Helm / Kustomize 模板不展开，带 `{{ }}` 的 YAML 会被标为模板并跳过，要先 `helm template` 渲染；`.env` 只看目标目录根部，`deploy/prod/.env` 这种多环境布局要单独指定目录再跑一次；YAML 格式的 OpenAPI 规范需要环境里有 PyYAML，没有就先转成 JSON；K8s 的最小 YAML 解析不支持锚点合并 `<<: *x` 与多行 flow 集合，这类文件先用 `kubectl apply --dry-run=client -o yaml` 规范化。

**5. 分级的取舍要团队自己定。** 22 条 info 里有相当一部分（`K011` 未指定 namespace、`K019` default SA、`DF015` CMD shell 形式）在具体项目里可能有合理解释。我的做法是：high 必须清零并作为 CI 门禁；warn 每条要有人认领；info 每季度扫一次，挑其中几条升级成团队基线，而不是每次发布都对着它们纠结。

最后一点关于分工的体会，和我上一篇写周报的案例是同一个结论：**让脚本管确定性，让模型管判断**。规则命中、行号、计数、排序、报告结构全在脚本里，所以复跑结果稳定、可进 CI；WorkBuddy 负责的是「这 15 条里哪几条在你这个项目里是真问题」「SQL 这三条要怎么拆成两阶段迁移」——这部分我全都核对了一遍，其中扩展-收缩的拆法、`total_fee` 与 `amount` 并存过渡这两处，是它给的方案比我原计划更稳的地方。

## 六、怎么复用

**1. 装技能。** 六个技能都在 SkillHub，按 slug 搜索安装；也可以直接从开源仓库取目录放进本地技能目录：

| slug | 作用 |
|---|---|
| `release-readiness-check` | 总入口：五项一起跑 + 门禁结论（五个检查器已内置，装这一个就够） |
| `dockerfile-check` | 单项：Dockerfile 17 条规则 |
| `k8s-manifest-check` | 单项：K8s 清单 17 条规则 |
| `sql-migration-check` | 单项：迁移 SQL 16 条规则 |
| `openapi-breaking-diff` | 单项：OpenAPI 3.x 破坏性变更比对 |
| `env-sync-check` | 单项：`.env` 三方对齐 |

只想跑其中一类、或者需要更细的参数（`--dialect` 指定 SQL 方言、`--example` 指定 `.env` 示例文件、`--env` 指定要对比的环境文件之类），再装对应单项技能；总入口内置的五个检查器参数与输出和单项技能完全一致。

**2. 第一次跑，先别开 `--strict`。** 存量项目第一次跑大概率一片红。先跑不带 `--strict` 的报告模式，把 high 列成一张表，分两三个迭代清掉；清零之后再把 `--strict` 挂上 CI，从此只拦新增。

**3. 三条命令就够用**：

```bash
# 本地：出一份报告
python3 scripts/release_check.py . --openapi-base api/openapi.v1.json --out ./release-report.md

# CI：有 high 就拦（旧规范拿不到时用 --skip openapi，别喂空 JSON）
python3 scripts/release_check.py . --skip openapi --strict --out release-report.md

# 单项深挖：报告里某项超过 10 条时
python3 scripts/k8s_check.py k8s/
```

**4. 别把它当成唯一的关卡。** 它的价值是「便宜到你每次都会跑」，不是「全」。
