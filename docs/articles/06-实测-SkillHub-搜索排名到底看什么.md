# 我们 113 个技能，40 个真实查询里 0 个进前三——SkillHub 搜索排名到底看什么

> 全部数字来自 2026-09-21 对 `https://api.skillhub.cn` 的只读、匿名调用。
> 样本：一个个人账号、113 个技能、40 个查询、两张完整的结果表。
> 核心结论只有一条，我会连同「它哪里站不住」一起写出来。

## 一、先说那个把我钉在椅子上的数字

我拟了 40 个「真人会怎么打字」的任务型查询——上线前检查、线上故障排查、简历优化、做PPT、报税、记账、旅行规划……全是动词或名词短语，不是职业称谓。然后一条条搜，统计我们自己那 113 个技能出现在第几位。

| 位置 | 命中我们技能的查询数 |
|---|---|
| 进前 3 | **0** |
| 进前 10 | 3 |
| 进前 20 | 4 |

40 个查询里有 36 个，翻完前 20 条也找不到我们任何一个技能。

我不太信，于是同一天测了两遍：16:40 用官方 CLI 的 `skillhub search --json`，21:35 直接打原始搜索接口。**两次结果完全一致。**

那天晚上我先浪费了大概一个小时在一个特别蠢的地方上：官方 CLI 返回的 `slug` 是 `@owner/slug` 这种带前缀的形式，原始接口返回的是裸 `slug`，owner 单独放在 `namespace.handle` 里。

```bash
# 官方 CLI：slug 形如 @owner/slug
skillhub search 记账 --json     # → "slug": "@<owner>/<slug>"

# 原始接口：slug 是裸的，owner 在 namespace.handle 里
curl -s "https://api.skillhub.cn/api/v1/search?q=记账&limit=20"
# → "slug": "<slug>", "namespace": {"handle": "<owner>"}
```

我拿 CLI 那套 slug 去比对原始接口的结果，三次读错——第一次以为我们一个都没上榜，第二次以为上了八个，第三次才发现是我自己在拿两种格式做字符串相等。**如果你也要做这种统计，先把两边的 slug 归一化，再谈结论。**

## 三、我的读法：分数几乎只看「查询占了名字多长」

下面是**我的推断**，不是平台说明。证据就是上面两张表。

**1）名字覆盖率是主项。** 把两张表按「查询字数 ÷ 名称长度」排一下，分数几乎是单调的：

- 完全相等（4/4、2/2）：**≈ 0.10**
- 2 字查询落在 4 字名里：**≈ 0.067**
- 2 字查询落在 5 字名里：**≈ 0.063**
- 2 字查询落在 6 字名里：**≈ 0.054**
- 2 字查询落在 12 字名里：**掉到地板线以下，不进前 20**

最能说明问题的是同一个后缀在两个查询下的不同命运：我们的「旅行规划专家.Skill」和「记账预算专家.Skill」都是 12 字，前者被 4 字查询覆盖了三分之一，拿到 0.053 排第 6；后者只被 2 字查询覆盖六分之一，直接沉底。**同样的命名法，只因为查询长度不同，一个上榜一个消失。**

**2）描述不参与排序。** 表一第 9 名描述 28 字、第 10 名描述 727 字，分数只差 0.001；表二里「描述出现查询 7 次」的商家记账助手排最后一名（0.051），「出现 0 次」的记账工具排第二（0.067）。描述字数和关键词堆砌次数都**没有重排任何结果**。我原本准备写一篇「怎么写描述抢排名」，这张表把它删掉了。

**3）下载量只是很小的尾项，不是主项。** 两条相反方向的证据：

- 它不可能是主项：表一第 5 名 349 次下载和第 6 名 16 次下载**分数完全相同**（都是 0.053）；第 8 名 317 次和第 7 名 15 次也一样。下载量差 20 倍，分数差 0。
- 但它确实在起作用：表一前两名名字完全一致（都叫「旅行规划」），691 次下载的排第 1（0.102），44 次下载的排第 2（0.092），**差 0.010**。表二里五个 6 字名按下载量 931 / 475 / 408 / 337 / 175 排下来，分数是 0.057 / 0.054 / 0.054 / 0.053 / 0.051，严格单调。

合起来看，最省事的解释是：**下载量是一个量级很小的平局打破项，名字对不上的时候它救不了你。**

**4）名字对不上的，统一掉到一条约 0.050 的地板价上。** 表一第 14、15、18、20 名——编程专家.Skill、self-improving、腾讯文档、Find Skills，四个和「旅行规划」毫无关系的技能，分数是平的 0.050/0.049，**并且这四个在「记账」查询下原封不动地又出现一次**。它们就是平台热榜的前几名。

这解释了一个我一直没想通的现象：搜「保险怎么选」这种没人用来当技能名的长句，返回的全是百万下载的头部技能。那不是语义匹配，那是**匹配不上时的兜底**——搜索退化成了热榜。

## 四、这个读法哪里站不住

我必须把边界说清楚，不然上面那节就是过度拟合。

**样本只有 2 个查询、1 个晚上。** 两张表加起来 33 条结果，来自两个中文双字/四字任务词。英文查询、长句查询、生僻词我一条都没测。

**我看不到排序代码。** 平台没有公开检索实现，我没有任何内部信息，也不打算猜它用的是 BM25 还是别的。上面全部是从输出反推的黑箱描述。

**榜单本身会抖。** 同一个「旅行规划专家.Skill」，21:35 那张表里是第 6，21:45 的复测是第 7。**十分钟内动了一位。** 所以名次差 1–2 位的对比不要当证据用。

**我自己这两张表里，至少有两处我解释不了：**

- **位置似乎也算分。** 同为 4 字名，「记账工具」（记账在前）0.067，「乖猫记账」（记账在后）0.057；同为 5 字名，「记账小助手」0.063，「家庭记账本」0.054。长度一样，分数差一档。我怀疑前缀命中有加成，但**只有这四个点，不足以下结论**。
- **「Accouting Skill」是个反例。** 它的显示名里根本没有「记账」二字，却拿到 0.057，明显高于 0.050 的地板。说明被检索的字段不止显示名——可能是 slug、可能是描述在「名字完全不命中」时才启用、也可能是别的。**我不知道，没测。**

**怎么证伪我这套说法**（这才是重点）：

1. 发两个内容完全相同、只有名字不同的技能——一个用 2 字查询词做全名，一个用同样的词加 8 个字后缀。如果两者分数相近，「覆盖率主导」就错了。
2. 找一个名字里**完全没有**查询词、但分数显著高于 0.050 的技能（Accouting Skill 就是候选）。把它的 slug 和描述拆开看，如果是描述起了作用，我第 2 条结论就得改写。
3. 找一个下载量差两个数量级、名字长度相同、分数却差 0.02 以上的配对。找到了，「下载量是小尾项」这条就废了。

任何一条成立，请直接拿数据拍我。

## 五、于是我改了 14 个名字，以及我没抄的那一行

问题其实在一开始就埋下了：**我们是按「角色」命名的，用户是按「任务」打字的。**

求职专家.Skill / 个税申报专家.Skill / 运维专家.Skill——用户不会搜「求职专家」，他们搜「简历优化」「报税」「线上故障排查」。更糟的是那个「专家.Skill」后缀：它给每个名字额外加了 6–8 个字符，把一个本来能命中的技能硬生生压到 0.050 的地板线以下。

对照一下排在前面的那些名字：报税助手、简历优化、记账小助手、旅行规划。**它们就是任务短语本身。**

## 六、差点骗过我的坑：`Published` 不等于上线

改完名要复测，这时候撞上今晚最阴的一个坑。

CLI 发布成功会打印：

```
✓ Published: skillId=… status=None
```

我一开始把这行当成「已上线」。**它只是「已入队」。**

一个新版本要变成 `latestVersion`，得先过两道安全扫描：`securityReports.keen` 和 `securityReports.sanbu`，状态从 `queued` / `排队中` 变成 `benign` / `安全，无风险`。在排队期间：

- `/api/v1/skills/{slug}/versions` **查不到**这个新版本；
- 但技能详情里的 `stats.versions` **已经 +1** 了。

两个接口同时在对我说不同的话。如果你只看其中一个，要么以为发布丢了，要么以为已经生效。

更要命的是队列长度不归你控制。09-21 我去看平台的 `newest` 排序，**全站最新一个上线的技能，时间戳是 09-20 16:01**——也就是说扫描队列对所有人积压了 29 个小时以上。不是我的技能有问题，是那天整条流水线就这么慢。

**规则：任何改名/改描述的实验，都不要从「发布时间」开始读数，要从「上线时间」开始读。** 判断依据只有一个——两份 `securityReports` 都变成 `benign`，并且 `versions` 接口能列出新版本。在那之前测到的名次，测的是旧名字。

这也是上面那张表右列全是「（待补）」的原因：写这篇的时候，改名还在队列里。

## 七、你可以自己跑的三条命令

全部只读、匿名，不需要登录。请自觉限速，相邻请求隔 1.2 秒以上。

**① 把任意查询的前 20 名连分数一起打出来**（换掉 `q=` 就行）：

```bash
curl -s "https://api.skillhub.cn/api/v1/search?q=记账&limit=20" \
  | python3 -c "import sys,json;[print(round(r['score'],3), len(r['name']), r['name'], r['namespace']['handle'], r['downloads']) for r in json.load(sys.stdin)['results']]"
```

**② 看你自己新发的版本到底上线没有**（读两份安全扫描报告）：

```bash
curl -s "https://api.skillhub.cn/api/v1/skills/<你的slug>" \
  | python3 -c "import sys,json;d=json.load(sys.stdin)['skill'];print(d.get('latestVersion'));print(d['stats']);print(json.dumps(d.get('securityReports'),ensure_ascii=False,indent=2))"
```

**③ 对照着看版本列表有没有真的多出来一条：**

```bash
curl -s "https://api.skillhub.cn/api/v1/skills/<你的slug>/versions" | python3 -m json.tool
```

②和③对不上的时候，以③为准——②的 `stats.versions` 在排队阶段就已经加过了。

## 八、我想要的东西

这篇的样本薄得我自己都不舒服：**两个查询、一个晚上、一个账号。** 所以最后这段是正经的请求，不是客套。

**请跑一下第①条命令，把你那张表贴出来。** 我特别想要这三类：

1. **英文查询和长句查询**——我全部的结论都建立在中文双字/四字词上，这是最可能崩的地方。
2. **名字里完全没有查询词、分数却高于 0.050 的技能**——每多一个这样的反例，「只看名字」这个读法就少一分可信度。
3. **你自己改名前后的名次对照**——如果你也在用「XX 专家」这类后缀，删掉它，隔一天再测一次。这是唯一能把我这套推断变成因果的实验，而我一个人做不出对照组。

数字对不上就直接说对不上。我上一篇写下载量机制的文章，结论被自己推翻了三次，**每一次都是因为有人给了我一个我手上没有的数据点。**
