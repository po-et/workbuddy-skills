# 用 WorkBuddy 把一周的 Git 提交整理成可溯源的迭代周报

**所处行业与岗位**：互联网软件研发，后端 / 全栈工程师，兼任小组迭代汇报。

**用 WorkBuddy 完成的工作**：每周一早上，把小组上周在 Git 仓库里的提交整理成一份迭代周报，发给技术负责人。要求每条"完成事项"都能点回具体的 commit，不能出现"优化了若干问题"这种无法验收的话。

以前这件事要 40 分钟：翻 `git log`、对工单、回忆"这个 commit 到底解决了什么"。现在是一次 WorkBuddy 任务，加上我人工核对，10 分钟以内。

## 一、输入材料

- 一个本地 Git 仓库（已 `git fetch`）。本文用我自己的开源仓库 [po-et/workbuddy-skills](https://github.com/po-et/workbuddy-skills) 做演示，时间窗 2026-09-09 至 09-16，共 26 个提交。任何仓库都一样，**不需要 token，内网 GitLab 也能跑**，因为只读本地 git log。
- 工单系统（可选）。这个仓库没有接工单系统，本文正好演示"没有工单系统怎么办"。
- 汇报对象：技术负责人。决定了周报保留全部六节，而不是给上级的三节精简版。

## 二、WorkBuddy 配置

- **Skill**：`iteration-report`（迭代周报生成器），开源，[SKILL.md 与脚本全部公开](https://github.com/po-et/workbuddy-skills/tree/main/skills/iteration-report)。它由三个脚本和一份报告模板组成：`collect_git.py` 采集提交，`collect_issues.py` 采集工单（可选），`render_report.py` 渲染骨架。**判断性内容（每条改动交付了什么价值）由 WorkBuddy 填写，脚本只做数据与统计**——这是它和"让 AI 直接总结 git log"的本质区别：数据部分零幻觉，推理部分可核对。
- **模式**：Ask 模式。重组周报是纯文本推理，不需要 Craft 模式的多步执行，积分省很多。
- **权限**：默认权限即可，只读本地目录。
- **不需要**专家、连接器或 MCP。

安装方式：在 WorkBuddy 的「专家·技能·连接器 → 技能」里搜索"迭代周报生成器"安装；或把仓库里 `skills/iteration-report` 文件夹放进本地技能目录。

[截图 1：技能市场里的「迭代周报生成器」详情页，或本地技能目录里的 SKILL.md]

## 三、操作步骤

**第 1 步：发任务。** 新建任务，输入：

```text
用迭代周报生成器给 ~/code/workbuddy-skills 这个仓库生成 2026-09-09 到 2026-09-16 的迭代周报，汇报对象是技术负责人。
```

WorkBuddy 读取 SKILL.md 后先做前置检查：确认仓库路径、时间窗、是否接工单系统。我回答"不接工单系统"。

[截图 2：WorkBuddy 的前置确认问题与我的回答]

**第 2 步：采集数据。** WorkBuddy 执行采集脚本，终端回显：

```text
✓ out/git.json: 26 commits / 1 authors / 0 条提交信息需反推 / 0 个风险信号
```

"0 条提交信息需反推"是脚本对提交信息质量的评估；如果一堆 `fix`、`update`，它会标出来，让 WorkBuddy 去读 diff 反推意图，并在报告里注明「推断」。

**第 3 步：出现问题——外部 issue 被当成了工单。** 渲染出的第一版报告，"本期交付"一节冒出五个工单 `[3712] [4787] [5368] [5601] [5602]`，全都指向同一个提交 `16fc70f`。查了一下：那条提交的正文里写着"上游已有 issue #5368/#5602 ……PR #5601 被关闭"，采集脚本默认按 `#数字` 提取工单号，把**别人仓库的 issue 编号**当成了本项目工单。

处理方式：这个仓库根本没有工单系统，让 WorkBuddy 重跑采集并加上 `--no-issues`（这个参数就是这次踩坑后给 Skill 补的，v0.1.2 起可用；有工单前缀的团队用 `--issue-pattern 'WB-(\d+)'` 只认自己的编号）。第二版报告里这五个假工单消失，26 个提交全部进入"未关联工单的提交"列表，等 WorkBuddy 按价值聚类。

[截图 3：第一版报告里的假工单，与重跑命令]

**第 4 步：WorkBuddy 填判断性内容。** 模板里有 6 处 `AGENT_FILL` 标记。WorkBuddy 把 26 个提交按"交付价值"聚成 5 条：开放平台提交前校验器与打包脚本、研发效能专家团与两个独立专家、两个 CLI 连接器（Mermaid、Draw.io）、hookify 插件移植的缺陷修复、Buddy 应用配置包。每条后面挂着 commit 短 hash。

我核对了两处：一处它把"文档更新"归入了交付项，我要求移到"内部优化"；一处它写了"提升了审核通过率"，这是数据里没有的结论，按 Skill 的"不编造"原则删掉。

[截图 4：WorkBuddy 输出的最终周报（第一节与第六节）]

## 四、产出物

一份 Markdown 周报，固定六节：本期交付 / 数据概览 / 风险 / 遗留 / 下期计划 / 数据说明。节选：

```markdown
# 迭代交付报告　2026-09-09 ~ 2026-09-16

## 一、本期交付
- **开放平台提交前校验器与统一打包脚本**：技能/专家/连接器三类包本地校验，避免上传后反复被解析器打回
  - 溯源：`9621bb8` `4882811` `52a34d9` `97e374e` `cbc31dc`
- ……

## 二、数据概览
- 时间窗：2026-09-09 至 2026-09-16
- 仓库数：1　提交数：26（不含 merge）　参与人数：1
- 改动规模：171 文件，+7778 / -68 行

## 三、风险
_未命中自动风险信号（单提交改动 >30 文件、revert/hotfix 关键词、多人改同一文件）。仍需人工判断。_

## 六、数据说明
- 未接入工单系统，第四、五节数据缺失
- 26 条提交未关联工单，交付项由 WorkBuddy 按内容聚类，已人工核对
```

**验收标准**（发出去之前我按这个检查）：

1. 每条交付项后面有 commit 号，随便点两条能对上。
2. 报告里没有数据之外的结论（"提升了""优化了体验"这类词要有依据）。
3. 第六节诚实列出缺口——这一节反而是技术负责人最爱看的。

## 五、几点经验

- **让脚本管数据、让模型管判断**，周报才可验收。整份周报里模型只写"价值判断"，而且每条都被 commit 号钉住。
- **"数据说明"一节不要删**。缺工单系统、提交信息质量差，都是团队的改进信号，写出来比藏起来有用。
- 提交信息写规范（`feat(scope): 做了什么`）比任何 AI 都更能提升周报质量——这次 26 条提交 0 条需要反推，就是因为提交信息本身合格。
- 遇到工具误判（外部 issue 当工单）不要手改结果，改采集参数重跑，否则下周还会错。

Skill 与本文使用的全部脚本开源：https://github.com/po-et/workbuddy-skills （MIT）。
