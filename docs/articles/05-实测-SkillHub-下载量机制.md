# 我把自己的结论推翻了三次：SkillHub 的下载量到底是怎么来的

> 四天、113 个技能、三份每日快照、208 组配对观测。
> 这不是成绩单——我们 113 个技能加起来 1872 次下载、0 收藏、0 评论、0 安装。
> 这是一份**把黑箱拆开的过程记录**，包括三次把自己的结论推翻重来。

先把丑话说前面：**这篇文章里有三个结论是错的，而且是我自己写下来又自己删掉的。** 过程全部保留——"我怎么发现自己错了"比"最后结论是什么"更可复用：结论会随平台改版过期，证伪的手法不会。

所有数字附来源和样本量，没测实的一律标"推测"并写出**怎么证伪**。

## 一、起点：一个不该出现的分布

SkillHub（skillhub.cn）是 WorkBuddy 的技能市场。我们用个人账号 `indiv-captain` 发了一百多个技能，然后撞上第一个问题：**作者看不到自己技能的下载量。** 官方 CLI 的 15 个子命令没一个打印 `downloads`，但服务端其实返回了：

```bash
# 官方 CLI：拿到了完整响应体，但只打印安全扫描字段
skillhub skill reports dev-workflow-pro --namespace indiv-captain --json \
  | grep -oE "downloads|installs|stars|comments"
# （无输出）

# 同一个接口，直接 GET
curl -s "https://api.skillhub.cn/api/v1/skills/dev-workflow-pro" | python3 -m json.tool | grep -A6 '"stats"'
# "stats": {"comments": 0, "downloads": 81, "installs": 0, "stars": 0, "versions": 1}
```

数字本来就在响应里，是 CLI 打印前筛掉的。于是写了个只读采集脚本，每天跑一次全量快照按日期存成 CSV。第二天把两份快照一减，出来的东西不太对劲：

```
09-18 → 09-19，95 个配对技能的下载增量分布：
{0: 69, 1: 8, 2: 9, 3: 1, 5: 7, 22: 1}

09-19 → 09-20，113 个配对技能的下载增量分布：
{0: 4, 4: 8, 5: 65, 6: 8, 7: 22, 8: 2, 9: 3, 10: 1}
```

第二行才是真正刺眼的：**113 个内容完全不同的技能，65 个恰好 +5**，中位数 5，全部落在 +4 到 +10 这个极窄区间里。这里面有纯 Markdown 的方法论（65 行），有带脚本的检查器，有 09-16 上架的老技能，也有 09-19 才发的新技能。**内容、是否带脚本、上架时长全都不一样，增量却一样。**

真实用户的分布是长尾的：少数技能很多下载，大部分是 0。这种"人人有份、份份差不多"的形状只能是机器。

## 二、第一次推翻：「发布一次 = 5 次下载」

**第一版结论（09-19 写的）：一次发布动作 ≈ 换来 5 次下载。**

依据看起来很硬——把 09-18 → 09-19 的 95 个技能按"昨天有没有发布动作"分组：

| 分组 | 技能数 | 24 小时下载增量 |
|---|---|---|
| 昨日升版本重发 | 7 | **每个恰好 +5** |
| 昨日新上架 | 18 | 每个 +5 或 +6 |
| 昨日无任何发布动作 | 69 | **+0** |
| 例外：`dev-workflow-pro`（无发布动作） | 1 | **+22** |
| 例外：`engineering-skills-index-zh`（无发布动作） | 1 | +2 |

25 个有发布动作的样本几乎全是 +5，69 个没动的全是 0。当时的解释是：平台的 AI 评测和安全扫描流水线在发布后拉了一次包，每次算 5 次下载。

顺带还得出一个很像样的推论：`dev-workflow-pro` 在**没有发布动作**的情况下 +22，是唯一的真实用户信号；它是纯 Markdown 的"伞形入口"，描述覆盖周报/上线/故障这类高频意图——所以该多做伞形技能。

**怎么被推翻的**：第二天数据一到就塌了。09-19 → 09-20，**我们没有重发任何老技能**，但 113 个里 109 个在涨，平均 +5.4。"发布动作"这个自变量根本不存在，因变量照常变化。问题不在结论错，在于**它只有一天的样本，却被写成了因果**。

## 三、第二次推翻：「下载量 ≈ Agent 自动调用次数」

第一版塌了之后我去看了排行榜前 100，做了第二版。这一版当时非常确信，因为有四条互相印证的证据。

**证据一：上架时长和下载量没关系。** 取 `skillhub skill rankings --type all` 前 100（门槛 76,308 次下载）：

| 上架天数 | 个数 | 下载中位数 |
|---|---|---|
| ≤30 天 | 10 | 167,018 |
| 31–90 天 | 27 | 128,171 |
| 91–180 天 | 19 | 133,323 |
| 180 天以上 | 44 | 129,838 |

相关系数 **r = 0.06**。上架 30 天内那批中位数反而最高。

**证据二：4 天能进前百。** `育儿大师.Skill` 上架 4 天、66.9 万次下载。其他新秀：露禾论文 6 天 30 万、防诈专家 11 天 14.5 万、dev-expert 18 天 56 万。

**证据三：这些新秀的描述都在指挥 Agent 主动触发。** 育儿大师原文："只要用户的问题涉及孩子（0-18 岁）的养育……**即应触发本技能，无需用户明确**"；anti-fraud："**当对话中冒出**转账、验证码……"——不要求用户提问，对话里出现就触发。

**证据四：我们自己是完美的反面对照。** `dev-workflow-pro` 写的是"**当用户提到**周报、上线、故障……时使用"——要求用户先说出那个词。量级差三个数量级。

再加上官方 Q&A 第 12 条：开放平台的技能"在技能市场展示和**被 Agent 自动调用**时，拥有更高的权重"——平台自己把它当成一件可度量的事。

四条证据指向同一个结论：**downloads 不是"有人点了下载"，而是"Agent 自动调用了这个技能"；决定量级的是描述触发面有多宽。** 这个结论很好用，能直接推出行动方案，我甚至已经把三组对照实验设计好了。

**怎么被推翻的**：写实验判读标准时，我需要确认"基线到底稳不稳"，于是多导出了一个字段——`updated_at`。

## 四、第三版（当前）：`updated_at` 是抓取时刻的标记

把 09-19 → 09-20 的 113 个技能按 `updated_at` 有没有变拆开，结果是这样的（详情接口里这个字段叫 `updatedAt`，我们的快照 CSV 里记作 `updated_at`，下同）：

| 分组 | 个数 | 下载增量 |
|---|---|---|
| `updated_at` 发生变化 | 109 | +4 ~ +10，**无一为 0** |
| `updated_at` 未变 | 4 | **全部 +0** |

未变的四个：`code-review-zh`、`pr-description`、`secrets-scan`、`skillhub-publish-helper`。

**关键在于那天我们没有重发任何技能。** 这 109 个的 `updated_at` 是平台侧自己动的：`access-log-stats` 从 `2026-09-18T05:45:17Z` 跳到 `2026-09-20T07:41:23Z`，同期下载 10 → 15。

把前一天也回查了一遍（原始记录里留的待办），09-18 → 09-19 的 95 组配对同样干净：

| 分组 | 个数 | 下载增量 |
|---|---|---|
| `updated_at` 变化 | 26 | +1 / +2 / +3 / +5 / +22，**无一为 0** |
| `updated_at` 未变 | 69 | **全部 +0** |

两天合计 **208 组配对观测：135 组 `updated_at` 变了、全部增长，73 组没变、全部零增长，没有一个例外。**

**结论：基线下载增量来自平台自身的流水线抓包，`updated_at` 精确标记了它何时抓取。** 与 Agent 是否调用无关，与描述触发面也无关。第二版作废。

回查还顺手杀死了第一版那个"唯一真实信号"：`dev-workflow-pro` 那天 +22，`updated_at` 从 `09-18T06:00:50Z` 变到 `09-19T00:04:36Z`——**它也在被抓取的那 26 个里面**。`engineering-skills-index-zh` 的 +2 同理。两个信号一个都不剩。

### 这一版最可能错在哪里

这个反驳是我自己想到、目前无法排除的：

**如果 `updated_at` 的语义只是"这条记录上次被写过"，而下载计数本身也会写这条记录，那"`updated_at` 变了"和"下载量涨了"就是同一件事的两种说法——相关性是同义反复，证明不了"抓包"。**（推测，需确认。）

**怎么证伪**：找一个下载确定由真人产生的样本——在干净机器上手动 `skillhub install` 一次——看 `updated_at` 会不会跟着动。会，这版就得重来第四次。**这个实验我还没做，欢迎你替我做**（第八节有命令）。

## 五、仍然没解开的谜

最核心的问题还是黑的：**流水线每次抓取只贡献个位数增量，解释不了头部的百万量级。** 编程专家 112.8 万、tencent-docs 111.2 万、dev-expert 123.0 万——不可能是每天 +5 累出来的。

已**被排除**：上架时长（r = 0.06）、内容形态（伞形入口与窄工具同为 +5）、描述触发面（已被 `updated_at` 否定）。**没排除**：端内 Agent 的真实调用、平台推荐位、我们看不见的运营动作。

我们账号没有任何一个技能进过榜单（去重后 319 个榜单技能里属于 `indiv-captain` 的：0 个）。把 1872 原样写出来就是想说清楚：**本文样本全落在基线区间，对百万量级没有发言权。**

## 六、方法论：三件可以直接拿走用的东西

### 1. 用一个"平台侧时间戳"把噪声减掉

这是最大的收获，而且不限于 SkillHub。任何计数指标，只要同时受"平台自动行为"和"真实用户行为"影响，你就需要一个**能标记平台行为发生时刻的旁证字段**。在 SkillHub 上是 `updated_at`，换个平台可能是 `last_indexed_at`、`etag` 或某个版本号。

有了它，判据就从"增量是多少"变成：

- 只统计 **`updated_at` 未变的日期区间**上的下载增量，那才是"非流水线增量"
- 一个技能若在 `updated_at` 没动的情况下下载量仍上涨，**那才是真实需求的证据**
- 截至目前，我们 113 个技能里**一例都没有**

反过来说，此前所有基于"日增中位数"的判断全都混着噪声，包括那个让我兴奋了一整天的 +22。

### 2. 单日数据不能下因果结论

第一版结论成立于一天的数据，第二天就死了。现在的规矩是：**任何"A 导致 B"的说法必须在至少两个独立的日期区间上复现，否则只记作"观察到的现象"。**

听着像废话，但当你手里 25 个样本全是 +5、对照组 69 个全是 0 时，"规律太干净了肯定对"的冲动是真实存在的。**分布干净恰恰该提高警惕**——干净通常意味着背后是机器。

### 3. 三组对照：一定要有"发布对照组"

验证"改写触发面能不能拉高下载量"的实验是这样设计的：

| 组 | 处理 | 样本 | 作用 |
|---|---|---|---|
| **实验组** | 重写 description 触发面，正文不动，升版本重发 | 12 | 看自变量 |
| **发布对照组** | **只升版本号重发，描述与正文均不动** | 4 | 排除"重发本身带来提升" |
| **空白对照组** | 完全不动 | 其余约 97 | 测平台基线 |

**中间那一组是整个设计的关键。** 没有它，实验组涨了你分不清是触发面起作用还是重发起作用——而重发一定会推 `updated_at`、一定带来 +5。很多"我改了 X 然后涨了"的经验贴，缺的就是这一组。

判读标准要提前写死，不能等数据出来再定：

- 实验组日增中位数 ≥ 发布对照组的 3 倍且持续 2 天 → 假设成立
- 两组无显著差异 → 假设不成立，回到机制探索
- **两个对照组都显著上涨 → 是平台侧变化（比如一轮全量抓取），本轮数据作废重来**

第三条是被现实教出来的：09-19 → 09-20 那天 109 个技能同时涨就是一轮全量抓取，当时若正在跑实验，整批数据都得扔。

**已知局限**（这实验也还没出结果）：样本小（12 vs 4 vs 97）；实验组是伞形与角色专家，与对照组形态不同；三天窗口可能不够。

## 七、顺手扒出来的六条平台冷知识

都是做别的事情时撞出来的，每条附复现命令。命令全部只读、匿名、不带鉴权头。

### 1. `tags` 不是关键词，是版本指针

我们给一百多个技能精心写了中文关键词标签。结果详情接口返回的 `tags` 是这样的：

```bash
curl -s "https://api.skillhub.cn/api/v1/skills/dev-workflow-pro" \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print(d['skill']['tags'], d['skill']['labels'])"
# {'latest': '0.1.1'} {'requires_api_key': 'false'}
```

`tags` 是 npm 式的 dist-tag（版本别名），`labels` 是系统标志。**不是搜索关键词。**

更麻烦的是另一半：官方 CLI 的 frontmatter 解析器在源码注释里写明"仅支持 `key: value` 与 `key: [a, b]`"，逐行 `partition(":")`，**不含冒号的行直接跳过**。标准 YAML 块状列表因此被**静默吃掉**，上送的 payload 里 `tags: []`，全程无警告。

（"我们的标签为空是被解析器吃掉的"属于推理，**需确认**。证伪方法：把 tags 改成 `[a, b]` 行内写法升版本重发，若搜索接口随后出现非空 tags 则成立。）

### 2. `category` 是平台按内容自动判定的

真正的分类体系是 `category` 和 `subCategories`，而**我们发布时从未指定过**：

```bash
for s in sre-expert dev-expert parenting-expert; do
  curl -s "https://api.skillhub.cn/api/v1/skills/$s" \
    | python3 -c "import sys,json;d=json.load(sys.stdin)['skill'];print(f\"{d['slug']:20s} {d['category']:18s} {d.get('subCategories')}\")"
done
# sre-expert           it-ops-security    ['日志分析', '监控告警']
# dev-expert           dev-programming    ['代码生成', '代码审查']
# parenting-expert     life-service       ['健康管理', '本地生活', '家庭']
```

**推论：描述写什么，直接决定落进哪个品类。** 这比填 tags 重要得多。顺便一个让人清醒的对照，我们 113 个技能 vs 平台前 100：

| 品类 | 我们（113） | 前 100 |
|---|---|---|
| dev-programming | **65** | 7 |
| it-ops-security | 22 | 0 |
| ai-agent | 17 | **22** |
| content-creation / office-efficiency / knowledge-management / design-media | 4 | **50** |

**58% 的技能挤在前 100 里只占 7 席的品类里**，而前 100 的四个主力品类我们合计只有 4 个。

### 3. 官方 CLI 把详情接口的 downloads/stars 过滤掉了

复现见第一节。`fetch_remote_search_results()` 重组搜索结果时没带出 `downloads/installs/stars`；`skill reports` 打的是同一个详情接口，但只打印 `securityReports`。**这不是权限问题**——读源码可确认，CLI 对这三个只读接口本来就不带 `Authorization`。

### 4. HTTP 566 是 WAF 按 `dockerfile` 路径前缀误伤

`dockerfile-check` 的详情接口与评测接口连续 4 天返回 HTTP 566。一开始以为是包有问题，差点改包重发烧配额。逐路径对比之后，规律非常干净：

```
/api/v1/skills/dockerfile-check                  → 566
/api/v1/skills/dockerfile-check/evaluation       → 566
/api/v1/skills/DOCKERFILE-xyz                    → 566   ← 大小写不敏感
/api/v1/skills/dockerfile-nonexistent-xyz123     → 566   ← 该 slug 根本不存在
/api/v1/skills/a/dockerfile-check                → 566   ← 任意层级的路径段
/api/v1/skills/dockerfileabc                     → 404   ← 后面紧跟字母则放行
/api/v1/skills/xdockerfile-check                 → 404   ← 不在段首则放行
/api/v1/skills/my-dockerfile-helper              → 404   ← 不在段首则放行
/api/v1/skills/docker-compose-check              → 200
/api/v1/search?q=dockerfile-check&limit=1        → 200   ← 同一个词放 query 里不拦
```

复现（把 slug 换成上表任意一行）：

```bash
curl -sI "https://api.skillhub.cn/api/v1/skills/dockerfile-nonexistent-xyz123" | head -3
# HTTP/2 566
# server: TencentEdgeOne
# content-type: text/html; charset=UTF-8     ← HTML 拦截页，不是 JSON
```

**"是通用敏感文件防护规则（拦 `/Dockerfile` 这类源码泄露探测）误伤了 slug 路径段"属于推测，需确认**——证伪方法：平台方查边缘规则，若命中的不是敏感文件规则则不成立。但"段首 `dockerfile` + 词边界才拦、slug 存不存在都一样"**是上表实测**。任何人发 `dockerfile-lint` 都会踩同一个坑。

![图3：HTTP 566 的逐路径对照表（终端 curl 输出）]()

### 5. 发布配额约 100 次 / 滚动 24 小时，不按日重置

09-17 晚上约第 100 次成功发布后全面拦截。接着 +1 小时重试仍拦（**本地日期已翻篇**）、+14.5 小时重试仍拦（**UTC 日期也已翻篇**），连未改动的对照技能也拦，同期读接口完全正常——两条"按日重置"的假设都被直接否掉。

最符合的解释是**滚动 24 小时窗口、上限约 100 次**——**推测，需确认**：平台不返回任何配额字段，窗口是不是 24 小时、上限是 100 还是 90，我们没做二分实验。

另有两条是实测、无推测成分：**失败的发布请求一样消耗配额**；被限流后要对**同一项**等 10/20/40 分钟重试，**跳过去发下一个只会更快耗尽额度**。

### 6. 无扩展名文件被拒收

目录里放了 `LICENSE` 或 `NOTICE`，上传报 `400 不允许的文件类型: LICENSE`。许可证只能写进 frontmatter 的 `license`。实测能通过的：`.md` / `.py` / `.yaml` / `.csv`（未穷举）。坑在于**本地 `--dry-run` 不拦**，要到服务端才知道，而失败的请求一样烧配额：

```bash
$ ls ./my-skill
SKILL.md   LICENSE   NOTICE
$ skillhub publish ./my-skill --dry-run
✓ Dry-run passed: my-skill@0.0.1        # 本地过了，上传会 400
```

反向的坑：ClawHub 拒收 `.pyc/.pyo/.pyd`，但**接受**无扩展名文件——和 SkillHub 正好相反。

```
skillkit new      从模板生成技能骨架（必填字段一个不少，坑点写在注释里）
skillkit lint     格式校验 + 五维质量打分 + 逐条改进建议
skillkit build    生成发布副本，自动处理已知的拒收规则
skillkit doctor   发布前体检：能不能发
skillkit budget   发布配额与节奏规划
skillkit stats    查询上架技能的真实指标（downloads / stars / AI 评测分）
skillkit pitfalls 打印内置的平台规律表（区分实测 / 文档 / 推测）
```

最后一条是我最想安利的：`skillkit pitfalls` 给每条规律标了**置信度**——「实测」/「文档」/「推测（需确认）」。标推测的**不要当事实引用**。

```bash
python3 -m skillkit pitfalls --confidence 推测     # 只看不可靠的那些
python3 -m skillkit pitfalls --json                # 机读
```

### 想验证我说的对不对？跑这三条

**这是我最想要的。** 我们的样本是一个账号、113 个技能、全落在基线区间里；你的不一样，尤其如果你有下载量过万的技能。

**① 看你自己技能的 `updated_at` 规律**（只读，不需要登录）：

```bash
# 连续两天各跑一次，比较 downloads 和 updated_at
curl -s "https://api.skillhub.cn/api/v1/skills/<你的slug>" \
  | python3 -c "import sys,json;d=json.load(sys.stdin)['skill'];print(d['updatedAt'], d['stats'])"
```

问题很具体：**在你的技能上，"`updated_at` 变了"和"下载量涨了"是不是也严格同进同退？** 如果你找到反例——`updated_at` 没动但下载量涨了——那就是我们找了四天没找到的第一例真实需求信号，请务必告诉我。

**② 替我做那个我做不了的证伪实验**：在干净机器上手动 `skillhub install <你的slug>` 一次，立刻查 `updated_at` 有没有动。如果人工安装也会推它，第四节那版结论就是同义反复。

**③ 如果你的技能下载量过万**，你手里就有我完全没有的东西——头部量级是全文唯一还全黑的部分。

批量跑（自带 ≥1.3 秒限速，追加写 CSV）：

```bash
python3 -m skillkit stats <slug1> <slug2> --namespace <你的handle> --csv metrics.csv
```

## 最后：一个人怎么测一个黑箱

四天里真正起作用的动作只有三个，都不需要资源：

1. **找到一个平台没打算给你、但确实存在的字段。**（`stats` 一直在响应体里，只是 CLI 没打印。）
2. **每天存一份原始快照，只追加不覆盖。** 没有第二个时间点，一切都只是截面——第一版就死在这上面。
3. **找一个能标记平台行为的旁证字段，把噪声减掉。** 这之前我们所有分析都在给噪声编故事。

前两版结论我写下来时都相信是对的。**现在回看，最危险的时刻恰恰是证据"互相印证"的时候**——那四条证据全都建立在同一个未经检验的前提上（downloads 反映用户行为），它们印证的只是彼此，不是事实。打破它的不是更多证据，是一个当时看起来完全无关的字段。
