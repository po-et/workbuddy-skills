# 设计稿：incident-brief 线上问题排查简报

状态：设计稿，未实现。这是本仓库的**招牌技能**，值得先把设计定死再写代码。

---

## 1. 要解决的痛

线上出问题时，人最痛的不是"不知道怎么修"，而是**在四个系统之间来回跳、手动对齐时间线**：

```
告警平台 → 日志平台 → 监控大盘 → 变更/发布记录 → 工单系统
   ↑                                                  ↓
   └──────────── 人肉在这中间跳 15 分钟 ───────────────┘
```

这 15 分钟发生在事故最紧张的时刻，而且**每次都一样**。这正是 Agent 该干的活。

---

## 2. 核心产品判断：不下结论，给证据链

这是整个设计最重要的决定，也是与市面上"AI 根因分析"类工具的根本区别。

**不要让 AI 输出"根因是 X"。** 理由：

1. 事故场景下，一个自信但错误的结论会把人带进沟里，代价远大于不给结论
2. AI 拿不到全部上下文（灰度状态、业务背景、上下游口头约定）
3. 一旦错一次，工程师就再也不信这个工具了

**应该输出：按可疑度排序的候选，每个候选带证据、反证、和一句可验证的推论。**

```
候选 1：14:23 的配置变更（可疑度 高）
  支持：错误率抬升起点 14:23:40，与变更时间差 40s
  反证：该配置只影响 B 集群，但 A 集群同样有错误率上升
  可验证推论：若成立，A 集群错误应为下游传导，检查 A→B 调用链错误码
```

最后一行是关键——**它让工程师 30 秒内就能证实或排除这个候选**。这比任何"根因判定"都有用。

## 3. 输入

| 入口 | 形式 | 说明 |
|---|---|---|
| 告警 ID | `incident-brief ALERT-123` | 最常用 |
| traceId | `incident-brief trace=abc123` | 单请求追查 |
| 时间窗 + 服务 | `incident-brief svc=order-api 14:00~14:40` | 无告警的手动排查 |

缺失信息一律**问**，不猜。尤其是时间窗——猜错时间窗会让整份简报失去意义。

## 4. 数据源适配器

四类信号，每类一个接口。**这是护城河所在**：接口稳定，内部实现可换。

```python
class LogSource:      # 日志
    def query(self, service, since, until, level=None, keyword=None) -> list[LogEntry]

class MetricSource:   # 监控指标
    def series(self, service, metric, since, until) -> TimeSeries
    def anomalies(self, service, since, until) -> list[Anomaly]

class ChangeSource:   # 变更（发布/配置/扩缩容/DDL）
    def changes(self, service, since, until) -> list[Change]

class TicketSource:   # 工单
    def recent(self, service, since, until) -> list[Ticket]
```

**公开版实现**（可入库、可发市场）：

| 接口 | 公开实现 |
|---|---|
| LogSource | Loki / Elasticsearch / 本地日志文件 |
| MetricSource | Prometheus |
| ChangeSource | GitHub / GitLab Releases + Deployments |
| TicketSource | GitHub Issues / Jira |

**内网实现**：单独的私有包，`entry_points` 注册，**绝不入公开仓库**。见第 8 节。

## 5. 处理流程

### 第 1 步：确定时间窗

以告警触发时刻为锚点，取 `[T-30min, T+10min]`。同时向前多取 2 小时用于**基线对比**——不知道"正常长什么样"就判断不了"哪里不正常"。

### 第 2 步：并行拉取

四个数据源并行请求。任何一个失败**不阻塞其余**，但必须在简报里明写"某数据源不可用"。

缺数据比错数据危险，但**隐瞒缺数据**最危险。

### 第 3 步：时间线对齐（核心价值）

把四类事件归一化成统一结构 `(时刻, 来源, 类型, 摘要, 链接)`，按时刻排序。

这一步就已经交付了 80% 的价值——**一张对齐的时间线，人自己就能看出问题**。

### 第 4 步：异常起点定位

在指标序列上找**变化点**，不是找超过阈值的点。阈值告警只告诉你"现在坏了"，变化点告诉你"什么时候开始坏的"，后者才能对上变更。

简单可靠的做法：滑动窗口均值 + 标准差，取第一个连续 3 个点超出基线 3σ 的位置。不要上复杂算法，可解释性比精度重要。

### 第 5 步：候选排序

对每个变更事件打分：

| 因子 | 权重 | 说明 |
|---|---|---|
| 时间接近度 | 高 | 变更时刻与异常起点的距离，越近越可疑 |
| 作用域重合 | 高 | 变更影响的服务/集群是否覆盖异常范围 |
| 变更类型风险 | 中 | 配置 > 发布 > 扩缩容（配置变更生效快、回滚记录少） |
| 历史相关性 | 低 | 该类变更过去是否引发过同类告警 |

**排序不等于判定。** 输出时必须同时给反证。

## 6. 输出契约

```markdown
# 排查简报　<服务名>　<时间窗>

## 现象
一句话。什么指标、从什么值变成什么值、什么时候开始。

## 影响面
- 受影响服务 / 集群 / 用户比例（有数据才写，没有写「未知」）
- 是否仍在持续

## 时间线
| 时刻 | 来源 | 事件 | 链接 |
|---|---|---|---|

## 可疑候选（按可疑度排序，非结论）
### 候选 1：<变更摘要>　可疑度：高
- 支持证据：
- 反证：
- **可验证推论**：若成立，应能观察到 ___，验证方式 ___

## 已排除
- <项>：排除依据 ___

## 数据缺口
- <数据源> 不可用：<原因>。本简报未覆盖 <哪部分判断>。

## 建议下一步
1. 先验证候选 1 的推论（预计 2 分钟）
2. ...
```

**硬约束**：
- "可疑候选"一节的标题必须含"非结论"字样
- 每个候选必须有反证，写不出反证的说明证据不足，降级或删掉
- "数据缺口"一节即使为空也要保留，写"无"

---

## 7. 额度控制

事故场景下人会反复追问，上下文累积极快，额度会爆。

- 第 1、2、4 步**全部由脚本完成**，不进模型。只有第 5、6 步进模型
- 进模型的是**归一化后的时间线**，不是原始日志。原始日志几 MB，时间线几 KB
- 日志做采样和聚类：同模式日志折叠成 `<pattern> × N 次`，只保留首末各 3 条样本
- 追问时只带时间线摘要，不重传原始数据

---

## 8. 合规红线

1. 公开仓库只包含通用适配器（Loki / Prometheus / GitHub / Jira）
2. 内网适配器放在**独立私有包**，通过插件机制注册，公开仓库只留接口定义与一份 `adapter-template.py`
3. 简报产物含生产日志片段，**默认只写本地**，不上传任何云端；如需云端模型参与第 5、6 步，先跑脱敏（IP、手机号、身份证、token、内网域名）
4. README 显著位置写明："本技能会读取你的日志与监控数据，使用云端模型时请先确认脱敏配置"
