# 实验：改写触发面能否让下载量脱离基线（2026-09-21 起）

## 假设

SkillHub 的 downloads 约等于 Agent 自动调用次数；决定它的是描述里触发面的宽度与是否让 Agent 主动识别。
（依据见 `2026-09-21-下载量机制.md`；此为推测，本实验即为验证。）

## 现状基线

截至 09-20，131 个技能每个稳定约 +5 次/天，与内容、脚本、上架时长均无关。

## 三组设计

| 组 | 处理 | 样本 | 预期（若假设成立） |
|---|---|---|---|
| **实验组** | 重写 description 触发面（两段式主动触发），正文不动，升版本重发 | 12 个：6 伞形入口 + 6 角色专家 | 日增显著高于 5 |
| **发布对照组** | **只升版本号重发，描述与正文均不动** | 4 个：`dockerfile-check`、`curl-to-code`、`log-timeline`、`csv-profile` | 仍为约 5，用于排除「重发本身带来提升」这个混淆 |
| **空白对照组** | 完全不动 | 其余约 115 个 | 维持约 5 |

发布对照组是这次设计的关键——没有它，实验组涨了也分不清是触发面起作用还是重发起作用。

## 测量

每天跑一次 `python3 tools/metrics_snapshot.py`，比较三组的**日增中位数**，连测 3 天。
只看增量不看累计（累计被发布动作污染）。

## 判读标准

- 实验组日增中位数 ≥ 发布对照组的 3 倍，且持续 2 天以上 → 假设成立，把改写推广到全部技能
- 实验组与发布对照组无显著差异 → 假设不成立，触发面不是杠杆，回到机制探索
- 两个对照组都显著上涨 → 说明是平台侧变化（如一轮全量抓取），本轮数据作废重来

## 已知局限

- 样本小（12 vs 4 vs 115），且实验组本身是伞形与角色专家，与对照组的技能形态不同，存在形态混淆。
- 前 100 榜单有幸存者偏差，不能反推「宽触发面必然起量」。
- 三天窗口可能不足以让平台的调用分布稳定下来。
