# 下载量的机制（2026-09-21，含当日两次自我修正）

> **重要：本文开头的第一版结论「下载量约等于 Agent 自动调用次数」已被当日晚些时候的证据否定。**
> 请直接看文末「第三次修正」一节，那是目前最站得住的说法。中间过程保留，用于说明推断是怎么一步步收紧的。

## 结论

**SkillHub 的 downloads 不是「有人点了下载」，而极可能是「Agent 自动调用了这个技能」。**
（推测，需确认——依据是下面四条相互印证的观察，以及官方 Q&A 第 12 条的措辞。）

决定下载量的不是技能质量、不是上架时长、不是数量，而是**描述里的触发面有多宽、以及是否指挥 Agent 主动识别**。

## 证据

### 一、上架时长与下载量无关

取排行榜前 100（`skillhub skill rankings --type all`，样本 100，最低门槛 76,308 次下载）：

| 上架天数 | 个数 | 下载中位数 |
|---|---|---|
| ≤30 天 | 10 | 167,018 |
| 31–90 天 | 27 | 128,171 |
| 91–180 天 | 19 | 133,323 |
| 180 天以上 | 44 | 129,838 |

相关系数 r = 0.06。**上架 30 天内的那批中位数反而最高。**

### 二、4 天进前百

`育儿大师.Skill` 上架 4 天，669,133 次下载。其他新秀：露禾论文 6 天 30 万、防诈专家 11 天 14.5 万、anti-fraud 16 天 18.8 万、dev-expert 18 天 56 万。

### 三、这些新秀的描述都在指挥 Agent 主动触发

育儿大师原文：「只要用户的问题涉及孩子（0-18 岁）的养育、健康、行为、情绪、学习或亲子关系，**即应触发本技能，无需用户明确**」。

防诈专家：「当用户描述一个疑似诈骗的场景、短信、电话、链接、聊天记录、App、投资平台、招聘信息或转账要求……」——触发面铺满一整类对话。

anti-fraud：「**当对话中冒出**转账、验证码……」——不要求用户提问，只要对话里出现就触发。

### 四、我们自己的写法是反面对照

`dev-workflow-pro` 写的是「**当用户提到**周报、上线、故障……时使用」——要求用户先说出那个词。
结果：131 个技能每个稳定约 5 次/天，与内容无关，像是没被匹配到时的floor。

官方 Q&A 第 12 条：开放平台的技能「在技能市场展示和**被 Agent 自动调用**时，拥有更高的权重」——平台自己把「被 Agent 自动调用」当作一项可度量的东西。

## 可操作的结论

1. **描述的触发面决定一切。** 写「当用户提到 X」要求用户说出关键词；写「只要涉及 X 即应触发，无需用户明确」让 Agent 主动判断。后者的量级高三个数量级。
2. **品类决定天花板。** 前 100 的分类分布：ai-agent 22、content-creation 15、office-efficiency 13、knowledge-management 11、design-media 11、**dev-programming 只有 7**、data-analysis 7、professional 7、life-service 5。我们 131 个技能几乎全在 dev-programming。
3. **时间不是筹码。** 不需要「熬」，4 天就能起量。反过来说，写法不对熬多久都没用。
4. **收藏是稀缺信号。** 前 100 里 98 个有收藏，中位数 100 个，最高 4507。我们 0 个——但按头部比例（编程专家 4587 次下载换 1 个收藏），我们 1872 次下载出现 0 收藏属于正常，只是量太小。

## 伦理边界（自设，执行时严守）

把描述写成**准确覆盖技能真正能处理的场景**、并让 Agent 认得出来，是正当优化。
把**技能接不住的场景**也写进触发面去截流量，是骗调用——用户被路由到一个帮不上忙的技能，损害的是作者信誉与平台生态。

执行规则：触发面里的每一类场景，技能正文必须有对应的处理方法；写不出方法的场景不许写进触发面。

## 待验证

- 「downloads = Agent 自动调用」仍是推测。验证方法：改写一批技能的描述触发面，其余不动，观察 3 天增量是否脱离 5 次/天的基线。这是本次要做的实验。
- 前 100 的样本有幸存者偏差，不能反推「所有宽触发面的技能都会起量」。

## 补充发现（当日稍晚，均已主线程复现）

### 一、`tags` 不是关键词，是版本指针

详情接口返回的 `tags` 形如 `{'latest': '0.1.1'}`，是 npm 式的 dist-tag。
`labels` 是系统标志（`{'requires_api_key': 'false'}`）。
**我们为 130 多个技能精心编写的中文关键词 tags，在平台侧没有对应字段，等于无效劳动。**（不产生危害，但也不起作用。）

### 二、真正的分类是平台按内容自动判定的

`category` 与 `subCategories` 才是分类体系，且**我们发布时从未指定过**，是平台从技能内容推断的：

| 技能 | category | subCategories |
|---|---|---|
| sre-expert | `it-ops-security` | 日志分析、监控告警 |
| dev-expert（他人） | `dev-programming` | 代码生成、代码审查 |
| parenting-expert（他人） | `life-service` | 健康管理、本地生活、家庭 |

**推论：描述写什么，直接决定落进哪个品类。** 这比「填 tags」重要得多，也再次支持「描述是唯一杠杆」的判断。

### 三、我们的品类分布与头部严重错配

| 品类 | 我们（116 个） | 平台前 100 |
|---|---|---|
| dev-programming | **65** | 7 |
| it-ops-security | 22 | 0 |
| ai-agent | 17 | **22** |
| content-creation | 1 | **15** |
| office-efficiency | 1 | **13** |
| knowledge-management | 2 | **11** |
| design-media | 0 | **11** |
| data-analysis | 2 | 7 |
| life-service | 0 | 5 |

**56% 的技能挤在前 100 里只占 7 席的品类里**；而前 100 的四个主力品类（content-creation 15、office-efficiency 13、knowledge-management 11、design-media 11，合计 50 席）我们合计只有 4 个。

### 四、HTTP 566 的真实成因是 WAF 路径拦截，不是技能故障

复现：

```
/api/v1/skills/dockerfile-check/evaluation              → HTTP 566
/api/v1/skills/dockerfile-nonexistent-xyz123/evaluation → HTTP 566   ← slug 根本不存在
/api/v1/skills/docker-compose-check/evaluation          → HTTP 200
```

响应头 `server: TencentEdgeOne`，返回 HTML 拦截页。**凡路径段以 `dockerfile` 开头即被拦截，与技能是否存在无关**——推测是 WAF 防路径探测规则误伤（推测，需确认）。影响一整类命名，任何作者用 `dockerfile*` 作 slug 都拿不到评测报告。

### 五、`installs` 字段是启用的，此前记录有误

旧记录判断「installs 未启用」是错的。实测 319 个技能里 82 个 `installs > 0`（如 tencent-docs = 8,107）。
正确说法是：**口径未公开**，绝大多数技能为 0 的原因不明（推测，需确认）。

## 第三次修正：基线增量来自平台流水线，`updated_at` 是它的标记

### 决定性证据

把 09-19 → 09-20 的 113 个技能按 `updated_at` 是否变化拆开：

| 分组 | 个数 | 下载增量 |
|---|---|---|
| `updated_at` 发生变化 | 109 | +4 ~ +10，**无一为 0** |
| `updated_at` 未变 | 4 | **全部 +0** |

未变的四个：`code-review-zh`、`pr-description`、`secrets-scan`、`skillhub-publish-helper`。

**关键点：那一天我们没有重发任何老技能。** 这 109 个的 `updated_at` 是平台侧自己变动的（例：`access-log-stats` 从 `2026-09-18T05:45:17` 跳到 `2026-09-20T07:41:23`）。

### 结论

**基线下载增量来自平台自身的流水线抓包，`updated_at` 精确标记了它何时抓取。** 与 Agent 是否调用无关，与描述的触发面也无关。

因此「下载量 ≈ Agent 自动调用次数」**不成立**，本文上半部分基于该假设的推论应当作废。

### 仍未解释的部分

平台流水线每次抓取只贡献个位数增量，**无法解释头部技能的百万量级**（编程专家 112.8 万）。所以头部的量必然另有来源，这部分机制目前仍然未知。已排除的解释：上架时长（r=0.06）、内容形态（伞形与窄工具同为 +5）、描述触发面（尚无证据）。

### 方法论收获（这条比结论本身更有用）

有了 `updated_at` 这个标记，就能把平台噪声从数据里减掉：

- **只统计 `updated_at` 未变的日期区间上的下载增量**，得到的才是「非流水线增量」
- 任何一个技能若在 `updated_at` 未变的情况下下载量仍然上涨，那才是真实需求的证据
- 截至目前，我们 133 个技能中**尚未观察到任何一例**

这也意味着此前所有基于「日增中位数」的判断都混入了流水线噪声，包括 09-19 那次「dev-workflow-pro +22 是唯一自然流量」的判断——它当天的 `updated_at` 是否变动需要回查，在回查之前该结论不可用。

### 对进行中实验的影响

`docs/metrics/实验设计-触发面改写.md` 的三组设计依然成立——实验组与发布对照组都经历了重发，两组的流水线噪声同源，可以相消。但**判读时必须改为比较「`updated_at` 未变日期上的增量」**，而不是原定的日增中位数。
