## 问题 2：路径里带 `dockerfile` 的请求被边缘安全策略拦截，返回 HTTP 566

**现象**：`dockerfile-check` 这个技能的详情接口与评测接口都返回 HTTP 566，已持续 4 天。但根因不在这条技能记录上——**是 URL 路径里的 `dockerfile` 这个词被拦了**。

**复现步骤与实际输出**（2026-09-21）

```
$ skillhub skill evaluation dockerfile-check --namespace indiv-captain --json
Error: 无法获取评测报告 (HTTP 566): HTTP 566            exit=1

# 同一时刻、同一账号的三个对照技能全部正常
$ skillhub skill evaluation sre-expert         --namespace indiv-captain --json   -> 完整报告 14982 字节
$ skillhub skill evaluation k8s-manifest-check --namespace indiv-captain --json   -> 完整报告 15501 字节
$ skillhub skill evaluation curl-to-code       --namespace indiv-captain --json   -> 完整报告 14712 字节
```

再用 curl 逐个路径对比，规律非常干净：

| 请求路径 | HTTP | 说明 |
|---|---|---|
| `/api/v1/skills/dockerfile-check` | **566** | 详情接口 |
| `/api/v1/skills/dockerfile-check/evaluation` | **566** | 评测接口 |
| `/api/v1/skills/dockerfile` | **566** | |
| `/api/v1/skills/DOCKERFILE-xyz` | **566** | 大小写不敏感 |
| `/api/v1/skills/dockerfile-nonexistent-xyz123` | **566** | **该 slug 根本不存在，仍被拦** |
| `/api/v1/skills/a/dockerfile-check` | **566** | 任意层级的路径段 |
| `/api/v1/skills/dockerfileabc` | 404 | 后面紧跟字母则放行 |
| `/api/v1/skills/xdockerfile-check` | 404 | 不在段首则放行 |
| `/api/v1/skills/my-dockerfile-helper` | 404 | 不在段首则放行 |
| `/api/v1/skills/docker-xyz123` | 404 | |
| `/api/v1/skills/docker-compose-check` | 200 | |
| `/api/v1/skills/zzz-nonexistent-xyz123` | 404 | 正常的「不存在」 |
| `/api/v1/search?q=dockerfile-check&limit=1` | 200 | 同一个词放在 query 里不拦 |

拦截发生在边缘，不在业务侧：

```
$ curl -sI "https://api.skillhub.cn/api/v1/skills/dockerfile-check"
HTTP/2 566
server: TencentEdgeOne
eo-log-uuid: 11618783705078076774
content-type: text/html; charset=UTF-8        # 返回的是 HTML 拦截页，不是 JSON

正常路径对照：server: TencentEdgeOne + eo-cache-status: MISS（即回源了）
拦截页可见文本只有两个数字："566 <一串请求号>"
```

**持续性**：本仓库 09-18 / 09-19 / 09-20 三份每日快照里，`dockerfile-check` 均记录为 `found=False, http_status=566`；加上 09-21 当天，已连续 4 天。不是间歇抖动。

**判断**：像是一条通用敏感文件防护规则（拦 `/Dockerfile` 这类源码泄露探测）误伤了 slug 路径段。**（推测，需确认。证伪方法：平台方查 EdgeOne 规则，若命中的不是敏感文件规则则此推断不成立；「段首 `dockerfile` + 词边界才拦」本身是上表实测。）**

**期望行为**：`/api/v1/skills/{slug}` 及其子路径下的 slug 段不应被文件名类规则匹配；至少 566 应返回 JSON 而不是 HTML，好让 CLI 给出可读的错误。

**对作者的影响**：三重。该技能的指标永远读不到；作者会误判成「我的包有问题」而反复改包重发、白烧配额；任何人发 `dockerfile-lint` 这类 slug 都会踩同一个坑——这是条会持续产生新受害者的规则。

**建议**：给 slug 路径段加白名单或收紧该规则的匹配位置；同时让边缘拦截返回 `application/json`。

## 问题 5：frontmatter 解析器不是 YAML，标准写法的列表会被静默丢弃

原本想报的是「未加引号且含半角冒号加空格的值导致解析失败且不给行号」。**这条在 SkillHub 侧没复现出来**——它的解析器根本不是 YAML，照单全收：

```
$ cat SKILL.md
description: 用法: 直接调用即可

$ skillhub publish <dir> --dry-run
✓ Dry-run passed: fb-probe-colon@0.0.1      exit=0
```

严格 YAML 报 `mapping values are not allowed in this context` 的是开放平台的解析器，**仅历史记录（2026-09-16 实测），本轮未复现**。

但顺着查下去，发现了一个影响更大的问题。`parse_skill_md_frontmatter()` 的文档字符串自己写着：

> PoC 限定：仅支持简单的 `key: value` 与 `key: [a, b]` 列表语法，避开 PyYAML 依赖。

它逐行 `partition(":")`，**不含冒号的行直接 `continue`**。于是标准 YAML 块状列表会被吃掉。用 CLI 自己的这段代码跑我们一个真实技能包：

```
parsed 'version'       -> '0.1.0'
parsed 'display_name'  -> '技能作者.Skill'
parsed 'tags'          -> ''              # 源文件里是 8 个标签的块状列表
parsed 'examples_zh'   -> ''
parsed 'examples_en'   -> ''
isinstance(tags, list) -> False
=> publish 上送的 payload 里 tags: []
```

因为 `_post_publish_multipart()` 只在 `isinstance(tags, list)` 时才带上 tags，块状列表写法的标签会**一个都不上送，而且全程没有任何警告**。

旁证：搜索接口里我们 113 个技能的 `tags` 全部为 `[]`，而榜单 319 个技能里有 22 个带着非空标签（如 `agent-browser` 的 `['automation','browser','headless','web']`）。**「我们的标签为空是被这个解析器吃掉的」属于推理，需确认——证伪方法：把某个技能的 tags 改成 `[a, b]` 行内写法升版本重发，若搜索接口随后出现非空 tags，则推理成立。**

**期望行为**：支持块状列表，或遇到时明确报错并带行号。

**对作者的影响**：标签是搜索命中的字段之一。写了标签却被静默丢弃，作者会以为自己做了可发现性优化，实际没有，且毫无信号。

**建议**：换成真正的 YAML 解析；无法引入依赖时，至少对「值为空且下一行以 `- ` 开头」给出警告。

## 问题 8：`downloads` 与 `installs` 的口径没有定义，两者差 2–4 个数量级

**先更正我们自己的一条旧记录。** 本仓库此前记「`installs` 对绝大多数技能恒为 0，疑似未启用」。复现后**这个说法不成立**：

```
$ curl -s "https://api.skillhub.cn/api/v1/skills/tencent-docs"
腾讯文档 TENCENT DOCS (@tencent-adm)
stats: {"comments": 0, "downloads": 1111915, "installs": 8107, "stars": 305, "versions": 22}
```

`installs` 是通的。榜单去重后 319 个技能里，82 个（25.7%）的 `installs` 大于 0。

**真正的问题是口径不一致且无处可查**：

```
dev-expert        (@indiv-ebandao)   downloads 1,229,585   installs      0
parenting-expert  (@indiv-ebandao)   downloads   669,212   installs      0
tencent-docs      (@tencent-adm)     downloads 1,111,915   installs  8,107   (0.73%)
self-improving-agent                 downloads 1,222,853   installs 86,140   (7.04%)
find-skills                          downloads 1,005,617   installs 75,956   (7.55%)
self-improving                       downloads   410,062   installs 57,561   (14.04%)
smart-charts                         downloads   362,062   installs      8   (0.00%)
```

下载量超过 10 万而 `installs` 恰好为 0 的有 33 个。同时，我们自己 113 个技能连续三天（09-18 / 09-19 / 09-20 快照）`installs` / `stars` / `comments` 全部为 0，而 `downloads` 从 1084 涨到 1872。

`downloads` 具体计的是什么，同样没有定义。我们的观察是 09-19→09-20 的单日增量分布极窄：`{0:4, 4:8, 5:65, 6:8, 7:22, 8:2, 9:3, 10:1}`，113 个内容完全不同的技能里 65 个恰好 +5。**我们据此推测累计下载量里混着一条与内容无关的平台基线（可能来自评测与安全扫描流水线拉包），(推测，需确认)。证伪方法：平台方对照埋点，若 +5 并非流水线产生，则推断不成立。**

**期望行为**：文档一句话说明 `downloads` 与 `installs` 分别在什么动作下 +1，是否去重、是否包含平台自身的流水线拉取。

**对作者的影响**：作者要靠这个数判断「有没有人用、要不要继续做」。口径不明时，1872 次下载可能是 1872 个用户，也可能一个真实用户都没有——两种解读导向完全相反的决策。

**建议**：在 `/docs` 里补一节指标口径；若 `downloads` 含平台流水线，最好能拆出 `organic` 口径。


09-20 的全量快照也是 113/113 双双完成。

**历史记录**：2026-09-17 20:55 的 82 个全量抽查里，搜索索引可见 81/82（98.8%），而 AI 评测只完成 26/82（31.7%）——最早排队的已等待近 3 小时。**这个差异当时是真的，现在已经追平。**

**仍然存在的问题**：API 里没有任何字段告诉作者技能处在哪一段。详情接口返回
`authorVerifiedHandle / category / claim_state / claimable / createdAt / displayName / ext / iconUrl / isServiceized / labels / overviewMd / slug / source / stats / subCategories / summary / tags / updatedAt / verified`——没有 `status`、`auditStatus`、`publishedAt`。作者只能靠「搜得到吗」「评测 404 吗」两个间接信号自己拼。

**期望行为**：详情接口加一个 `pipeline` 状态对象（索引状态 / 安全扫描状态 / 评测状态各一个枚举 + 时间戳）；文档说明这是两条独立流水线、评测 404 不等于被拒。

**对作者的影响**：评测查不到时第一反应是「被拒了」，接着改包重发、白烧配额，而实际上只是批处理没跑到。

**建议**：文档先加一句「上架与评测互相独立，评测 404 表示尚未生成，不代表审核不通过」，成本最低。

不图换什么，只是让下一个作者少踩几次坑对双方都划算。若官方有更合适的反馈模板或渠道，请告知，我们按格式重填。

## 补充（09-23）：搜索不分词

复现：`GET /api/v1/search?q=请假条` 第一名是名为「请假条」的技能（0.079）；`q=写请假条` 或 `q=帮我写年终总结` 全部返回热榜兜底（0.050）。137 条带动词的自然语言查询里 91 条完全无匹配。建议：对查询做分词或前缀剥离（帮我/写/做/算/给我），否则用户按说话方式搜索时几乎搜不到任何技能。

## 补充（09-23）：三个影响终端用户的问题

1. **裸 slug 解析到别人的同名技能，用户会装错。** 复现：`GET /api/v1/skills/pr-description` 返回 `@user_79bcc5a2/pr-description`（ClawHub 来源，730 下载），带 `?namespace=indiv-captain` 才是原生作者的同名技能。按 CLI 默认用法 `skillhub install pr-description` 的用户，拿到的是哪一个取决于解析顺序（需确认）。同日新导入的镜像让 4 个原生技能的裸 slug 被「占位」。建议：同 slug 多作者时，详情/安装接口要求显式 namespace，或在结果里提示「存在同名技能」。
2. **newest 榜滞后约 12 小时。** 09-23 14:30 查询，newest 榜最新一条创建于 09-23 01:31；当天 12:00 以后上线的技能都不在榜。新作者最依赖的这个入口，恰好在他们最需要曝光的那几个小时里看不到。
3. **新技能品类迟迟不判定。** 09-23 上线的 46 个技能到当天 14:30 的 `category` 仍为空，品类页里找不到它们。
